## 1. User-locked scope
1. Usage-limit pause/resume is IN the MVP (flagship).
2. "Memory optimisation" = BOTH process supervision AND context/token economics.
3. The "Intent Next" design package is visual direction only (exception: limit-pause mechanics and the 8-state UI vocabulary).
4. Agent control on stdio; WebSockets only at the observation boundary. `harness serve` deferred post-MVP (review consensus).
5. Implementation runs via orchestrated workflows; all changes consolidated **unstaged** in the main workspace; merge/integration is never automated.

## 2. Problem statement
Coding-agent harnesses each own an agent loop (model calls, tools, permissions, context, native sessions) with different control surfaces and no portable session format. The product coordinates them without pretending they are interchangeable: goal → approved testable spec → isolated implementation → independent verification → merge-readiness; sessions that **pause on provider usage limits** (never respawn-loop), supervised processes (RSS watchdog, finite restarts, breaker, orphan reaping), full lineage (run/session/model/memory/evidence), model/harness changes only at safe boundaries, honest crash recovery, human in control of specs, permissions, integration.

## 3. Research conclusions (normative summary; evidence tiers in ORCHESTRATOR-NOTES §1)
- **ACP is the MVP control plane** for Claude Code + Codex via pinned official adapters (`@agentclientprotocol/sdk@1.2.1`, `claude-agent-acp@0.59.0`, `codex-acp@1.1.4`, Node ≥22.14). Adapters execute lockfile-pinned binaries only; codex-acp's platform binary arrives via lockfile-pinned `optionalDependencies`, no postinstall (verified — supply-chain concern resolved).
- **Precedent, stated precisely**: Intent by Augment v0.5.0 instantiates a single `ACPProvider` class for every interactive provider (claude-code, codex, opencode, pi, droid, cortex) after per-harness command resolution (`provider-registry.js:6-58,107`, re-verified locally). This proves feasibility of ACP-driving several harnesses; it does not prove portability, reliability, or market convergence. The SPI therefore keeps an executable non-ACP fallback seam (headless-JSON tier), not just a diagram box. No PTY tier: all 8 researched harnesses expose structured headless surfaces.
- **P2 compatibility gate (normative)**: before committing the rest of P2, run a live gate on both adapters covering permission mediation, cancellation, identity-confirmed resume, error-envelope visibility (incl. limit envelopes), and model-switch timeout/fallback. If the Claude adapter fails systemically (not anecdotally), the Claude Agent SDK adapter is promoted INTO the MVP as a correction. (Adapter risk anecdotes: switch flakiness #886, MCP injection loss #883, compaction invisibility #873, post-resolve updates #864 — treated as risks to gate, not settled facts.)
- **ACP has no rate-limit signaling** (closed StopReason enum: end_turn/max_tokens/max_turn_requests/refusal/cancelled). Claude adapter emits `-32603` + `data.errorKind='rate_limit'` (adapter convention, PR #582). Codex adapter emits `-32603` + `data.codexErrorInfo='usageLimitExceeded'` — a structured limit discriminator (source-verified in the pinned codex-acp@1.1.4 dist) with NO reset time; the richer RateLimitSnapshot telemetry (windows, resets_at) still never crosses ACP (#227 remains accurate for that signal). Classification design in §13 follows from this.
- **Model mechanisms are declarative per provider** (`modelMechanism`): current SDK = `session/set_config_option`; older deployments used `session/set_model`; others use env/CLI flags. Probe at initialize.
- Adapter roadmap after MVP: opencode (native `opencode acp`) → pi (in-process SDK / `--mode rpc`) → Droid/Auggie (native ACP; local installs stale — upgrade first) → Gemini. Grok Build: opt-in only (2026-07 privacy incident), never a default.
- Billing: API key is the documented path for Claude (third-party subscription OAuth barred by ToS 2026-02-19; billing-inconsistency issue #43333) and recommended for Codex automation. `doctor` reports auth per provider as `supported | detected_but_unsupported | unknown` — no categorical claims beyond evidence.
- SQLite: `node:sqlite` on Node 22.14.0 emits `ExperimentalWarning` (verified locally). Default driver = `better-sqlite3` behind the repository interface; the same contract tests run against `node:sqlite` to keep the swap live.

## 6. Domain model and state
### 6.1 Entities
`Run`, `SpecVersion` (immutable, content-hash), `Assignment` (role, spec hash, base commit, worktree, policy, wave/group id reserved), `SessionSegment` (one harness-native session; distinct ids: segment / ACP session / provider-native session / process-generation), `Turn`, `Event` (append-only, monotonic per-run sequence, idempotency keys), `Artifact` (content-addressed), `MemoryEntry` (§15), `Verification` (binds spec hash + base commit + implementation commit), `MergeReadiness`, `LimitIncident` (provider, limit kind, detection tier, resumes_at?, source, resolution), `ProcessSample` (aggregated projection; raw pruned), `Checkpoint` (§12.2).

### 6.2 State model — three orthogonal axes (no flat enum)
- **Run.phase** (workflow position): `created → specifying → awaiting_approval → approved → implementing → verifying → needs_remediation → implementing … → merge_ready` ; terminals: `cancelled`, `failed`. Supersession is not a Run.phase: modeled as `SpecVersion.status='superseded'` + `Assignment.status='stale'`; T3's `spec.superseded` event carries the follow-on phase (implemented in `src/domain/state.ts`, conformance-tested).
- **Assignment/Segment.suspension** (orthogonal, only while a child/segment is active or resumable): `none | paused_limit | paused_user | resource_exhausted | breaker_open | interrupted`. Suspension records `{reason detail, return_phase, in_flight_operation?, entered_at}`. Suspension never changes phase; resume returns to `return_phase`.
- **Segment.operation** (at most one in flight): `idle | prompt_turn | initial_config_pin | model_switch{from,to,requested_at} | checkpoint_write | git_op{kind} | resume_probe`. (P4a) `initial_config_pin` spans option discovery through §11.2 pin enforcement on a fresh spawn; `prompt_turn` only wraps actual prompt turns.
- **Active child is generation-tracked, never a boolean** (P4a): `activeChild {generationId, segmentId, status: spawning|active|stopping|stopped}`. `child.spawn.initiated` (P4a W2-3) marks the fresh generation `spawning` and opens the `initial_config_pin` window in the durable state; `child.spawned` (supporting event, carries role + pins incl. echo facts) is the only thing that marks a generation ACTIVE — appended strictly after pins succeed, closing the pin window; `turn.started`/`turn.completed` keep `operation=prompt_turn` truthful across prompt turns (so T4 is licensed on live ingest AND replay); pause/exit paths mark the generation `stopping` with a durable stop-intent (`child.stop.intent`); only a generation-MATCHED `child.stopped` confirms the stop — a late stop from generation N never clears N+1. Resume (T9/T12) records `resume_reentry_pending` (acked by `resume_reentry.completed`; startup/`resume` reclaim unacknowledged re-entries idempotently) and never marks a child active.
- **UI vocabulary is a projection**, never stored: Starting=spawn/handshake · Working=prompt_turn in implementing/verifying · Waiting on you=awaiting_approval or permission-wait · Paused—limit=paused_limit · Stopped=cancelled/paused_user · Done=merge_ready · Breaker open=breaker_open · Handed off=superseded-by-successor.

Rules: approval binds the exact SpecVersion hash. Verification binds spec hash + base + implementation commit. `merge_ready` requires evidence for every criterion. Remediation bound (default 3) exhaustion → `failed`, never false completion. Every transition is one idempotent event append + projection update in one transaction. **(P4a F1) Write-path atomicity (read-validate-append)**: the transition's STATE READ, its `applyTransition` validation, and the event-append + projection-fold all run inside ONE `BEGIN IMMEDIATE` (`transactionImmediate`) — factored as a single shared engine-write primitive that `ingest` (transition + engine-folded-supporting branches), `advanceWorkflowPhase`, and `pauseForLimit` all funnel through (`resume`/`completeCoordinationRound` open the same IMMEDIATE outermost so the inner append nests as a shared no-op; `appendTriggerWithEffects` takes an `alreadyInTransaction` flag to join, not re-open, the caller's txn). Because the read is taken UNDER the write lock, a trigger is always validated against FRESH state: a transition another CLI committed between this caller's decision and its write is SEEN, so an incompatible trigger is REJECTED (never appended folding a stale snapshot) — closing the cross-process lost-update / illegal-post-terminal-append window where e.g. a late child-crash could silently overwrite a committed cancel with cursor past both events, unrecoverable by replay. BOUNDARY: `RoleRoundProjection` `#saveRoleRound` is last-write-wins, protected by the F2 run-ownership lease, not this primitive. **(P4a W3-4) Coordinator-completion atomicity**: the `specifying → awaiting_approval` completion (`completeCoordinationRound`, shared by `start`/`spec revise`/the W2-5 coordinator re-entry) persists the spec-draft projection BEFORE the final workflow advance, both in ONE transaction, and the advance event carries the draft's `SpecDraftRef` (artifact hash == spec content hash + version + revision) — so replay can DETECT a lost/stale draft against the durable ref and `approve`/`run` refuse (`spec_draft_missing`/`spec_draft_stale`) with a recovery hint while `spec revise` re-drafts (rebuilding revision context from the completion ref + CAS artifact); a crash anywhere in the completion rolls back to `specifying` with the round re-drivable, never an approval-ready draftless run.

## 7. Specification contract
Coordinator returns a structured spec: goal; assumptions + unresolved questions; constraints + permissions; non-goals; ordered tasks + dependencies; acceptance criteria with stable IDs; verification commands + expected evidence; rollback/recovery notes; proposed implementor/verifier profiles (these become `run` defaults so `run` needs no profile args). Coordinator output is untrusted: schema-validated, ambiguous/untestable criteria rejected, stored immutable, and approved — **by default by a human, always explicitly; see §7.1 for the one opt-in exception.** `spec revise` (T2) supports review→revise rounds. Imported human specs supported (still approved explicitly). **Optional planning chat:** `start --enable-chat` persists the choice in run metadata and wraps coordinator drafting/re-entry/revision in an Agent Room foreground loop. The host forces the room to `127.0.0.1`, prints the invitation immediately, publishes coordinator turns, consumes the server-managed unread queue, honors addressed-only response guidance, and accepts no final spec before an external agent/human contribution. Room messages are untrusted planning input; the same schema/testability gate and a T1 approval remain mandatory. The default path never resolves, launches, or contacts Agent Room.

### 7.1 AMENDMENT (B2, 2026-07-25) — the human input gate becomes opt-out
**This section deliberately REVERSES a Rev-3 invariant.** §4.1 and §7 originally read "explicit human approval (always — no auto-approve path)", and §21 D7 rejected threshold-gated auto-approval. That absolute no longer holds, and the contradiction is recorded here rather than left silent.

**What changed.** `EngineConfig.approval: 'human' | 'auto'`, default `'human'`. Under `'auto'` the ENGINE binds the drafted spec hash itself the moment a coordinator drafting round completes (`start`, and a completed `spec revise` round) and the run proceeds to `approved` with no wait.

**Why.** The goal is a base system that builds software on its own (`docs/AUTONOMOUS-BASE-PLAN.md`). A run has two human gates — approve the spec (input) and merge the result (output). The merge gate is the more meaningful control: it is where code actually enters the repository. So the human gate MOVES from reviewing intentions to reviewing verified outcomes; it does not disappear. **Nothing auto-merges — §16 is unchanged, and that is the invariant that is not negotiable.**

**What is NOT relaxed** (each is enforced in code and regression-tested in `src/cli/commands.auto-approval.test.ts`):
- **Immutability + hash binding.** `'auto'` changes only WHO signs. The SpecVersion is still content-addressed and immutable, and T1 still binds the exact drafted hash (W1-F3). The engine NEVER fabricates a hash — the synthetic-hash path remains `--test-approve`, still refused unless `HARNESS_TEST_MODE=1` (§18), still test-only.
- **The same validation.** Auto-approval runs the SAME W3-4 draft-loss detection an explicit `approve` runs; a missing/stale draft refuses with the same code and exit. Auto-approval is a signature, not a bypass.
- **The §7 testability gate.** `assessSpecSemantics` is untouched and still rejects criteria with no concrete observable. Under autonomy it is the ONLY automated filter between a coordinator's plan and real work, so it must never be softened to make autonomy flow.
- **Auditability.** Every approval is evented `spec.approved {approvedBy: 'human' | 'auto'}`, folded into `EngineState.specApprovedBy`, and reported on the §16 merge-readiness record as `specApprovedBy` (plus an explicit warning line on the human surface). A merge reviewer is always told when nobody reviewed the intent.
- **Immutability of the choice.** The mode is pinned into the run's persisted config at `createRun` (W1-F5) and read from there, so autonomy can be neither granted nor revoked after a run starts.

**The failure mode this does not prevent:** a coordinator producing a coherent, testable, verifiable spec that is nonetheless the WRONG WORK. Nothing in the engine catches that. It is exactly what the merge review is for — and it is why the human gate moves rather than disappears. §21 D7's reasoning (a size heuristic auto-approving a small-looking authorization change, then the same actor implementing and "verifying" it) is answered by keeping the roles separate and the merge gate human, NOT by the input gate; D7 remains rejected as specified.

## 8. Role contracts (host-enforced; prompts follow the Augment template: frontmatter `{name, description, harness, model, roleReminder}`; body: Role → Hard Rules first → Workflow in order → Format spec → Tools → Completion report)
- **Coordinator**: read-only workspace; writes specs/exploration artifacts only; cannot approve own spec; cannot dispatch or mutate workflow state; `roleReminder` re-injected every turn.
- **Implementor**: writes only inside its assigned worktree; one approved spec version + bounded task scope; runs declared verification commands; returns changed files, diff, tests, exit statuses, risks, commit SHA; cannot change criteria or mark complete.
- **Verifier**: read-only on the exact implementation commit; maps every criterion ID to evidence it gathered itself (`passed | failed | unproven`; any failed/unproven blocks); the Coordinator's exploration artifact is available strictly as an **untrusted index bound to its source commit — never evidence**; structured fix-request output.
- Delegation depth ≤ 2, host-enforced. Harness-native subagent tools that conflict with orchestration are denylisted per profile (`conflictingBuiltinTools`).

## 9. Harness adapter SPI
Operations: `probe() · initialize() · createSession() · loadSession() · resumeSession?() · forkSession?() · prompt() · cancelTurn() · listConfigOptions() · setConfigOption() · resolvePermission() · classifyError(raw) · close()`.
- `resumeSession?` = native fast resume (no replay), returns `{resumed: 'native'|'replayed', identityConfirmed: boolean}`; `loadSession` = replay path. Conformance tests cover advertised-but-failed resume and identity mismatch. Native fork unused in MVP (successor lineage suffices); probed and recorded only.
- `classifyError` operates **only on adapter/protocol error envelopes** (JSON-RPC error responses, typed adapter errors, HTTP 429/Retry-After in API-key mode) → `{kind: usage_limit | auth | crash | protocol | unknown_provider_error, resumesAt?, source: structured|parsed, confidence}`. Free text inside agent messages is NEVER classified (a model merely *talking about* limits must not pause a run).
- Capability record: protocol+version, executable/package version, auth readiness (`supported|detected_but_unsupported|unknown`), create/load/resume/fork/cancel, model+mode+reasoning options, `modelMechanism`, permission-request support, MCP config support (report-only in MVP), checkpoint/export, `usageLimitReporting: structured|parseable|none`, `retryAfterTier: honored|forecast_fallback|forecast_only`, `usageAccounting: per_turn|none`, `conflictingBuiltinTools[]`, observed session identity. Unsupported capability → typed error; never silent degradation.

## 10. ACP transport (numeric limits normative)
### 10.1 Lifecycle
Resolve exact lockfile-pinned binary → spawn in own process group with identity nonce (`HARNESS_SPAWN_ID` env) → stdout exclusively ACP NDJSON; stderr retained bounded/redacted → initialize + capability probe (records fork/resume/config-option/mode support) → create/load session, confirm returned identity → prompts + normalized updates → cancel gracefully → escalate termination → close streams, reap process group (identity-verified, §14).
### 10.2 Limits and permissions
Handshake timeout 15s · turn timeout 30min · max protocol line 1MiB · decoded-event queue 1,000 (overflow = terminal event + cleanup) · stderr retention 64KiB head/tail · cancel grace 3s · terminate grace 2s. Malformed JSON, oversized lines, protocol mismatch, unexpected EOF → explicit terminal events. ## 11. Session and model semantics
### 11.1 Resume
Persist separately: segment id, ACP session id, provider-native session id, process-generation id, last completed turn + event cursor. Resume in place only when the adapter advertises resume/load AND confirms the same session identity; prefer `resumeSession` (native) over `loadSession` (replay); any ambiguity → checkpoint-linked successor (the portable correctness path). (P4a W2-5) Run-level resume RE-ENTRY is driven entirely from the durable `RoleRoundProjection` (round, role, serialized inputs, spec/base binding, exact implementationCommit for verifier rounds, checkpoint ref, stage, intended completion advance) + the §12.2 checkpoint + the persisted loop binding/worktree facts — never from a dead process's memory. (P4a F3 §5x) The §12.2 checkpoint is DERIVED FROM THE LOG, not from the `checkpoint ref` pointer: resume scans `checkpoint.recorded` for the LATEST-by-sequence event whose enriched binding (specHash + assignment) is compatible with the current round (reusing this same eligibility chain), so a crash between the atomic `checkpoint.recorded` append and the separate `checkpointRef` save no longer loses the checkpoint and cadence checkpoints (which never write `checkpointRef`) are visible; `checkpointRef` is only an optional fast-path cache hint (never atomic), and the specHash filter guarantees a superseded-spec checkpoint is never resurrected. A transactional ELIGIBILITY check precedes EVERY T9/T12/interrupted re-entry (manual `resume` and the scheduled-probe T9 alike): assignment open + non-stale AND `checkpoint.specHash == assignment.specHash == engine approvedSpecHash == current draft.specHash`; any mismatch is a typed refusal WITHOUT clearing the suspension (a superseded spec can never resurrect an old round). Re-entry ADOPTS the assignment worktree via the manager (mutex + §16.3; never creates): an interrupted implementor gets WIP-commit-or-reset reconciliation (recorded durably); an interrupted verifier is forced back to the persisted implementationCommit with verifier dirt DISCARDED and clean asserted, restarting on the SAME immutable binding — checkpointed passed criteria carry over only with same-spec/commit-bound evidence, and `worktreeClean` is always re-probed after adoption. The re-entered round going ACTIVE acks the pending re-entry (`resume_reentry.completed`); startup/`resume` reclaim unacknowledged pending re-entries idempotently.
### 11.2 Model switching (only at confirmed completed-turn boundaries on a live session)
Discover options → validate against advertised values → persist `model.switch.requested` → invoke per `modelMechanism` → await effective-value echo → persist `model.switch.confirmed` | `failed`. Timeout (default 60s) + one retry, then checkpoint-successor. Cross-harness switch is always a successor: inject approved spec + selected memory + mechanical checkpoint + evidence refs; record that native continuity was not preserved. A limit during `requested` (T5) → `failed_indeterminate` → successor with explicit model re-assertion. Example: Codex terra drafts spec → user pauses at approval → switch to sol → confirmed in-session or checkpoint-successor → sol proposes spec v2.

## 12. Persistence, checkpoints, crash recovery
### 12.1 Store
`better-sqlite3` (D6 resolved; `node:sqlite` experimental on 22.14 — same contract tests keep the swap live) behind repository interfaces. WAL; foreign keys; busy timeout; migration table; restrictive permissions; one logical writer; transactions wrap event append + projection; monotonic per-run sequence; idempotency keys on provider notifications and transitions. Large payloads: redact → hash → content-addressed artifact dir; SQLite keeps metadata + bounded previews. **Quotas (normative)**: per-run artifact quota 2GB, global 20GB (admission rejection + event when exceeded); telemetry (vitals) aggregated per-minute in projections, raw samples pruned (the §14 watchdog sample path folds every CLOSED per-minute window and prunes the raw rows it folded, so `raw_process_samples` stays bounded to the in-progress window; `status` reads the newest closed aggregate and falls back to the latest raw tick for the still-open window so RSS is populated as soon as sampling starts); job/subscriber/wait queues bounded with drop-oldest+replay or dead-letter; reference-aware artifact GC.
### 12.2 Checkpoint contract (mechanical, synchronous, no LLM anywhere in the pause path)
Content: segment lineage (predecessor harness/model/session/final turn) · last completed turn id + event cursor · spec hash + per-criterion state · constraints + permission policy · confirmed decisions · unresolved risks · failing tests · artifact/evidence refs · exact worktree state (HEAD sha, `git status --porcelain` snapshot, diff hash, lockfile-cleanup performed?, taint flags) · `incomplete_operation?` (recorded honestly — a mid-turn checkpoint does NOT claim completed work). **Atomicity**: artifact written to CAS first, then `checkpoint.recorded` event with its hash in the same transaction as the state transition; artifact-without-event is invisible to replay and GC'd; event-without-artifact is impossible (event commits after artifact fsync). (P4a F3 §5x) The `checkpoint.recorded` event DENORMALIZES the binding (`specHash`, `role`, and — for a dispatched round — `round`/`assignmentId`) so resume can DERIVE the latest binding-compatible checkpoint from the LOG ALONE (no N artifact loads), making "resume re-derives from the log" real for both the crash-before-`checkpointRef`-save window and cadence checkpoints. (P4a) The limit-pause path composes exactly this: `pauseForLimit` fsyncs the checkpoint artifact, then ONE atomic append carries the T4/T16 trigger + `checkpoint.recorded` + `limit.incident.recorded` + `child.stop.intent` (generation marked stopping); only then is the child cancelled/disposed, and the generation-matched `child.stopped` confirms — a restart at any crash point recovers idempotently (unreferenced artifact → GC'd; committed stop-intent without confirmation → identity-verified cleanup then `child.stopped`). A quota-rejected checkpoint write never blocks the pause: the run pauses without `checkpoint.recorded` (admission rejection recorded honestly). **Cadence**: every N completed turns (default 3) + before model switch, pause, verify handoff, graceful stop. (P4a W4-1) The completed-turn cadence is WIRED into the runtime: the service's role-session `prompt` boundary drives a per-run `CadenceTracker` (policy = `checkpoint.cadenceTurns`) that writes a `cadence` checkpoint (idle operation — a completed turn interrupts nothing) once N completed turns elapse; ANY checkpoint written (cadence or a safe-boundary pause/stop) resets the turn-count window so cadence never fires early. Narrative/LLM summaries are DEFERRED from MVP entirely; the mechanical core must be sufficient for successor context and is tested as such (§19-22).
### 12.3 Restart recovery
Never trust a stored PID alone; verify full process identity (§14) before any signal. Mark abandoned `running` work `interrupted` (T17); replay idempotent events to rebuild projections (this recovers ORCHESTRATOR state; the AGENT's in-context work is recovered only to the last checkpoint — the plan makes this distinction explicit); validate worktree (§16.3); resume confirmed session or checkpoint-successor. (P4a W4-4) `harness resume` also re-drives an UNSUSPENDED implementor/verifier run stranded at a role-completion boundary — the orchestrator died AFTER the round's `child.stopped` folded but BEFORE the next dispatch/verdict landed (implementor done → phase `implementing`; verifier round done → phase `verifying`, T23/T24 not yet applied). One `handleResume` dispatch gate (`suspension=none` ∧ round∈{implementor,verifier}/`completed` ∧ child stopped/absent ∧ phase non-terminal) routes it to `resolveResumeEntry`'s next durable step, GATED on §14 owner-liveness (`isRunClaimedByLiveProcess`) so a still-alive PEER's run is never double-driven. Implementor re-entry preserves partial WIP (§16.3 WIP-commit-or-reset); only the read-only verifier discards dirt. (P4a W4-4 residual) `isRunClaimedByLiveProcess` reads a durable RUN-ownership lease ({runId, ownerPid+start-time}) — NOT the per-child registry, whose record a clean child dispose removes: the lease is acquired at the outer entry of the implement/verify driver (both a fresh start-that-drives and a resume-that-drives) and released in its outer `finally`, so it is held ACROSS child rounds and survives the between-rounds child-dispose gap (implementor stopped, verifier not yet dispatched) where a live owner would otherwise hold no record — closing the last double-drive window. A lease whose owner pid is gone/recycled (§14 identity) does not claim the run and is reclaimed, so a crashed owner never blocks a legitimate resume. The SAME `isRunClaimedByLiveProcess` gate also guards the W3-4 coordinator re-drive carve-out AND the unacknowledged pending-re-entry carve-out, so EVERY resume re-drive path (coordinator, implementor, verifier, pending re-entry) is consistently owner-liveness gated. (P4a W4-2 Stage 1, review-6 F2) The lease is now EXCLUSIVE, not advisory: `acquire` is a COMPARE-AND-SWAP inside one `BEGIN IMMEDIATE` (the count-and-reserve shape) returning a BOOLEAN — it accepts iff the run is unclaimed, already self, or held by a provably dead/recycled owner (§14 liveness evaluated INSIDE the txn), so two concurrent reclaimers of one crashed run serialize on the write lock and the loser gets `false` (attack-e). The driver checks that boolean and WITHHOLDS (honest `RunOwnershipConflictError`, no double-drive) if it did not win, and acquisition happens BEFORE any worktree create/adopt or role work (not after). The lease is also extended to `runCoordination` (S4): a live coordinator round now holds it, so `isRunClaimedByLiveProcess` is TRUE during it (previously it acquired nothing, making the coordinator carve-out gate a production no-op).

## 14. Process supervision
- **Exit confirmation and barrier failure semantics (Round 6 closure)**: `signal_sent` means only that the verified SIGKILL path was accepted. Transport `dispose()` resolution is likewise NOT exit evidence for an identity-backed handle: adapters may return after leader exit while descendants remain. Disposal triggers an immediate watchdog resample, and only observed WHOLE-PGID absence permits durable finalization, cleanup, or capacity release; a missing leader with live descendants remains `exit_pending`. Opaque identityless handles retain their owned-disposal contract because no PGID exists to sample. RSS and provider-limit stops use one generation barrier with one bounded cancel path and one memoized disposal. The barrier commits the durable terminal outcome BEFORE removing registry/watchdog ownership or releasing reservation/concurrency capacity; commit, cleanup, or reservation-release failure retains a retry path and remains capacity-counted. If an ambiguity timeout abandons an abnormal/no-T22 waiter, a later absent PGID applies generation-matched T17 (breaker-exempt) before cleanup/release, so ownership cannot leak. Startup identity mismatch still withholds signaling and alerts, then independently samples the recorded PGID: absent reconciles as `confirmed_gone`, present remains skipped and owned. A graceful T22 persistence failure rolls `graceful_pending` back so later watchdog ticks retry; a rejected graceful or emergency T22 launches NO cancel, dispose, signal, or taint side effect. Failed or hung disposal without a captured identity resolves fail-closed, and its cancel, exit-confirmation, and durable-outcome retry timers remain REFERENCED because no registry/startup recovery route exists. Confirmed process exit is the natural `end_turn` race cutoff: a turn completed before confirmation stays completed; a buffered return after confirmed termination cannot overwrite `resource_exhausted`.
- **Identity**: registry persists {pid, pgid, process start-time, executable path, generation id, `HARNESS_SPAWN_ID` nonce, **owning-orchestrator pid + start-time**}. Any signal (watchdog, reaper, cancel) requires full identity re-verification; ambiguity → never kill, surface an alert. Startup reaping kills only identity-verified orphans. (P4a W4-0) Reaping is additionally OWNER-GATED: `reapOrphans` skips — never verifies, signals, or removes — any record whose OWNING orchestrator is still alive (self, or a live PEER, via the same owner-liveness check as the spawn-reservation store: `isAlive(ownerPid)` + start-time match, recycled-pid safe), reaping ONLY records whose owner is provably dead (or a recycled owner pid, or absent = legacy/unowned). This closes a pre-existing peer-kill bug where a `resume` in one process SIGKILLed a DIFFERENT live orchestrator's identity-unambiguous child (the withhold-on-ambiguity guard does NOT cover an unambiguous live peer). The owner pid is stamped = the registry's `#selfPid` at registration. (P4a W2-6) The identity is captured at the `RoleAdapterHandle` right after spawn, the registry store is DURABLE (backed by the existing SQLite projection layer), and the record is persisted BEFORE `child.spawned` commits — a crash anywhere after the OS process exists leaves a reapable record. Startup reaping (run at `resume`) additionally re-verifies the nonce by reading the child's env where the platform allows (darwin/linux best-effort): a contradicting or unreadable nonce WITHHOLDS the signal and surfaces a durable `process.identity.alert` event; a provably-GONE generation completes any committed stop-intent (`child.stopped` reason `startup_cleanup`, §12.2). (P4a W3-2) CROSS-PROCESS control: a `pause`/`cancel` issued from a SECOND CLI process only appends the intent — the live child runs in the FIRST process — so after the append the intent's owner routes the stop through this same durable registry (`stopExternalChild`): the FULL §14 identity (ps identity AND the env nonce) is re-verified and a signal is delivered to the child's process GROUP, WITHHELD+alerted on any ambiguity (never signal a recycled pid). `pause` sends one graceful SIGTERM; `cancel` escalates the §10.2 terminate ladder (SIGTERM → terminate grace → identity-verified SIGKILL, re-verified before each rung). The owning process observes the death through its transport and folds the generation-matched `child.stopped` (the existing runRole/T13 fold). A generation still live IN the acting process is left to the in-process stop path (limit pause, run-owned cancel) — never cross-signaled.
- **Watchdog**: RSS of the full process tree is sampled on the adaptive schedule and folded into the aggregated projection. Budget default 1024MB comes from the run's PINNED config, not the driving process: soft 75% → T21 warning; 100% → T22 v2 plus graceful mechanical checkpoint/cancel/dispose under the deadline (default 30s); hard emergency ceiling (default 150%) → identity verification, synchronous pre-signal T22 v2 persistence, SIGKILL, then worktree taint (§16.3). Identity mismatch records the identity alert but sends no signal and records no T22 v2, stopped child, taint, or resource exhaustion. The pre-signal hook accepts only an applied T22 v2 or an exact idempotent v2 replay; rejection aborts the transport side effects. Graceful callbacks are launched without blocking watchdog ticks, so sampling and deadline escalation continue while checkpoint/cancel/dispose is slow or hung. One generation shutdown barrier memoizes disposal and retains supervision, the process registry, spawn reservation, and concurrency slot until watchdog-observed WHOLE-PGID absence confirms an identity-backed exit; provider-limit shutdown enters this same barrier. Confirmation atomically finalizes `resource_exhausted` when licensed by durable RSS intent and never routes through T13, then cleanup/release occurs only after that commit. Watchdog termination **participates in the worktree mutex**: while a segment holds a git-op lease, kill waits for op completion or the emergency ceiling (which taints). A background sample tick that THROWS is caught by the scheduler, surfaced via a durable supervision-failure alert, and followed by later samples. The `ps` process-group/RSS adapter is **macOS-only** in the MVP; `package.json` declares `"os": ["darwin"]`, `doctor` warns elsewhere, and a GNU/Linux adapter remains roadmap.
- **Restarts/breaker**: window bound (default 5/10min, configurable 3|5|8) AND non-disableable per-assignment lifetime cap (default 10) AND no-progress detection (identical checkpoint content-hash across 2 consecutive restarts → breaker). `off` exists only behind an explicit `--unsafe-dev` flag and retains the lifetime cap. Exponential backoff between restarts; max elapsed recovery time (default 30min) → breaker. Limit-pauses never count (T4/T16). (P4b-2 §5cc) `restarts.autoRespawn` (`bounded`|`off`, DEFAULT `bounded` ON) governs the child-crash auto-respawn CONTROL FLOW ONLY — the window/lifetime breaker bound applies in BOTH modes (`off` removes only the automatic re-drive, reproducing P4a exactly; the safety bound is never disabled by it). (P4a W4-1) The `RestartBreaker` is WIRED into the runtime CHILD-crash site (`#interruptOnChildDeath`) — its sole caller; it consumes the durable lifetime counter (never re-tracked in-memory) plus its own time-decayed restart window keyed per assignment (run-id fallback for assignment-less spawns), and `breaker reset` (T15) clears that in-memory window alongside the durable counters. Orchestrator restarts (T17) are deliberately NOT routed through it. (P4a F4 §5x) The fast sliding window is now DURABLE: the restart `occurredAt` list is folded INTO `EngineState.counters.restartWindow` and PRUNED in the pure T13 reducer by the trigger event's own `occurredAt` against `windowMinutes` (never `Date.now`, hard-capped at the lifetime max) — ONE write riding F1's atomicity, never a second breaker store; the breaker DECIDES the fast `window_bound` off that durable list on EVERY `evaluateCrash` call (P4b wave-1 S5 §5cc: the in-memory deque is demoted to a re-hydratable observability cache, rebuilt from durable truth + the current crash each call — never independently accumulated — so a stale-generation crash whose T13 the engine REJECTS can never inflate the window and mis-gate a later respawn), so the window survives a fresh CLI process AND stays entry-for-entry consistent with the reducer-owned durable copy. `no_progress` and `recordProgress` are WIRED: `#interruptOnChildDeath` passes the latest checkpoint hash DERIVED from the log (F3's binding-compatible derivation) into `evaluateCrash` so no-progress can fire, and a round reaching `completed` calls `recordProgress` so an unrelated later crash starts a fresh recovery sequence instead of false-tripping `max_elapsed_recovery`.
- **Concurrency**: simple max-live-children guard (default 3) — the MVP is serial-per-run; RAM-tier scheduling + LRU eviction deferred to the parallel-waves phase (and then derived from available memory + measured per-process reservation, not copied constants). (P4a W3-5) The guard is wired into `runRole`'s spawn path: admission is refused (`MaxLiveChildrenExceededError`, before any spawn) at capacity, and the cap is GLOBAL across concurrent CLI processes. (P4a W4-8) Admission runs BEFORE anything durable OR any provider resource is created — ahead of the pending-round save AND ahead of `#adapterFactory.create` (which for the Codex path prepares the §17.1 H-1 isolated `CODEX_HOME` at creation time) — so a cap refusal leaks neither a durable pending round nor a temp `CODEX_HOME`; a resource-setup failure AFTER admission releases the durable reservation + in-process slot before propagating. (review-6 F8) The scheduled limit-probe spawn (`runScheduledProbe`'s throwaway session) goes through this SAME guard — admit before the adapter/`CODEX_HOME` is created, release on every exit path — so probes count against the global cap and cannot exceed `maxLiveChildren`. (P4a W3-5a) The count-and-reserve is ATOMIC across processes: each process reserves a durable spawn slot (a reservation record written BEFORE the spawn) inside a single serialized `BEGIN IMMEDIATE` write transaction that also counts identity-alive live slots — so two processes started concurrently serialize on the write lock and the N+1th observes the prior reservation, instead of both reading zero (the registry record alone lands only at `child.spawned`, leaving a TOCTOU window). A crashed peer's reservation (owner pid gone/recycled, §14 identity) is excluded and reclaimed, never holding capacity hostage or deadlocking; the slot is released on every `runRole` exit path. (P4a W4-4) A sibling durable store keyed by RUN (not generation) records a RUN-ownership lease ({runId, ownerPid + start-time}) — the owner/control channel — acquired for the WHOLE time a process actively drives a run (the implement/verify driver's outer entry, held across child rounds) and released in its outer `finally`; the consumer resume gates consult it (`isRunClaimedByLiveProcess`) so a between-rounds gap — where a clean child dispose has removed the per-child registry record but the owner is still alive — cannot let a concurrent `resume` double-drive the worktree. Same owner-liveness rule: a lease from a dead/recycled owner does not claim the run and is reclaimed (crash recovery, no deadlock). (P4a W4-2 Stage 1, review-6 F2) This lease is EXCLUSIVE: like the count-and-reserve, `acquire` is a compare-and-swap in one `BEGIN IMMEDIATE` returning a boolean (accept iff unclaimed/self/dead-owner), acquired BEFORE any worktree work; the driver refuses to drive (withholds) when it loses the swap to a still-live peer, and `runCoordination` holds the same lease so a live coordinator round is genuinely claimed (S4).
- **Self-supervision**: the orchestrator bounds its own memory (stream artifacts to CAS, bounded queues/projections per §12.1) and emits a heartbeat event (60s) so a stall is observable.
- **(P4b-1) Operator alerts** — a durable `alert.raised {alertId, kind ∈ limit_paused|resource_exhausted|crash|respawn|breaker_open|failover, role, generationId?, topic, detail}` (`runId`/`occurredAt` on the envelope; `detail` REDACTED via the §17.1 path) is FOLDED into the SAME `#atomicEngineWrite` transaction as its triggering transition — the single emit point scans the transition's engine-emitted `notify.requested` effects for an alertable topic (`paused_limit`→limit_paused via `pauseForLimit`; `resource_exhausted`→resource_exhausted on confirmed RSS exit; `interrupted`→crash and `breaker_open`→breaker_open via `#interruptOnChildDeath`) and rides one `alert.raised` per hit (alertId/idempotency-key DERIVED from the trigger's key). So an alert can never exist without its cause and vice-versa — a rejected trigger (stale-generation crash, double-pause) or a crash-injected alert append leaves NEITHER. `respawn` is now EMITTED by the P4b-2 auto-respawn wave — the successor spine raises it DIRECTLY (a standalone `alert.raised{kind:respawn, topic:respawn}` after the generation-matched T13 commits, not derived from a notify effect) on a healthy bounded auto-respawn, and the `crash` alert is SUPPRESSED for that crash (it auto-recovered — not operator-actionable). `failover` is likewise emitted DIRECTLY by the P4b wave-2 successor spine (`driveFailoverOnLimit`) — a per-step `alert.raised{kind:failover, topic:failover}` carrying the from→to lineage on each ladder escalation, plus a degrade-to-wait `alert.raised{kind:failover, topic:failover_exhausted}` on ladder exhaustion (T25) — never derived from a notify effect. Delivery is best-effort/at-least-once and DERIVED from the log (an `alert.raised` with no matching `alert.delivered {alertId, sink}`, the derive-don't-point pattern — no delivered cursor is the source of truth; a per-sink cache is an optional optimization): each un-acked `(alert, sink)` is handed to its registered `Notifier` then acked with `alert.delivered` (dedup by `(alertId, sink)`); a restart re-derives and re-delivers exactly the still-un-acked alerts once more. Sinks: `stderr` (a real CLI push) + a `status --json` `alerts` section (a pull view derived from the log, showing per-sink delivery state); the `Notifier` INTERFACE is the webhook/push/desktop seam — interface + registry + a no-op adapter ONLY in wave 1, NO concrete network adapter. Every CLI invocation over the shared store flushes un-acked alerts (the "startup re-derive").

## 15. Memory and context economics (MVP-tight)

Projection convention (normative, set during P1): acceptance criteria project onto `type:'constraint'` (always-preserved tier); current failures/failing tests project onto `type:'risk'`; `fact` and untrusted decisions rank below the named tiers. ## 16. Git worktrees and merge-readiness
- **16.0 Deliverable invariant**: `RoleRunner` is role-discriminated and every implementor path requires a runtime adjudicator, including dispatchless/direct and standalone entry points. `committed:true` requires a present `commitSha` exactly equal to host-read HEAD; `no_deliverable` prevents verifier spawn independent of optional dispatch metadata, and host-HEAD failures remain recoverable inside the protected role-flow boundary.
1. Require a git repo; resolve immutable base SHA. 2. Dedicated branch + worktree outside the primary checkout. 3. Single-writer lease per assignment. 4. Implementor confined to its worktree. 5. Record diff, tests, resulting commit. 6. Verifier inspects that exact commit read-only. 7. `MergeReadiness` only for the verified commit.
- **16.1 Pinned coordination source (strict-rejection decision)**: coordination runs in the primary checkout, not a managed detached checkout. Before `createRun`, canonicalize the repository root, resolve a full `HEAD^{commit}`, and require an empty ordinary porcelain status (tracked, staged, modified, and untracked paths; ignored build/cache paths remain outside this policy). Persist that SHA as the immutable run base. Production `createRun` requires the exact full `GitSha` at its type and runtime boundary; the public production legacy creator is removed, and only a production-build-excluded test fixture can manufacture old unpinned metadata. The shared SERVICE-LAYER guard takes a stable HEAD/status snapshot and rechecks HEAD to close its own TOCTOU, then compares the full SHA and clean status before initial coordinator dispatch, after coordinator output but before accepting the draft, before and after revision/coordinator re-entry, immediately before approval, and immediately before the first fresh implementation worktree. Refusal is structured as `workspace_unresolvable`, `workspace_dirty`, or `base_drift`, with pinned/current SHAs and dirty paths where available. Any primary-checkout edit during coordination invalidates that result; restore a clean checkout at the pinned SHA and re-enter the same round. Fresh worktree APIs accept only `baseCommit: GitSha`, re-resolve it, and reject missing, symbolic, short, unresolvable, or mismatched input. Both the standalone implementor entry and the implement/verify loop compare that input exactly with the run's durable pin before creating a worktree. One-time audited pinning exists only for persisted legacy runs; new starts never take it.
- **16.2 Mutex**: all `git worktree add/remove` serialized per repo (concurrent ops corrupt `.git/worktrees`). The supervisor's kill path respects git-op leases (§14). (P4a W3-5) The in-process `GitOpMutex` is complemented by a CROSS-PROCESS file-based advisory lease (a lock dir under the primary repo's `.git`, atomic `mkdir` gate) held around `worktree add/remove` — so a SECOND `harness` OS process on the same repo cannot race the git op; a lease held by a dead/recycled pid is reclaimed via §14 identity (pid + start-time), never waited on. (P4a W3-5d) A HOLDERLESS orphan (lock dir present but its identity file missing/unreadable/malformed — a process that crashed in the mkdir→stamp window or left a corrupt file) is likewise reclaimed after a bounded grace, never a permanent deadlock; the grace is long enough that a live acquirer mid-stamp is never falsely reclaimed.
- **16.3 Taint + validation**: emergency kills or deadline terminations mark the worktree TAINTED. Before any restart or verification on a worktree: remove stale `index.lock` (within the mutex), parse `git status`, verify HEAD readable, reconcile against the last checkpoint's recorded worktree state (dirty/partial → WIP-commit or reset-and-record; refusal to resume-in-place on mismatch). This runs before the lease releases at pause/kill time. (P4a W2-5) The WIP-commit path is the IMPLEMENTOR's reconciliation; an interrupted VERIFIER round is instead forced back to its persisted implementationCommit with verifier-created dirt DISCARDED (mutex-protected `discardToCommit`: stale-lock cleanup, hard reset, untracked clean, clean asserted) — a read-only verifier's evidence dirt is never preserved work.
- Readiness fails if: any criterion failed/unproven · spec hash changed · implementation commit ≠ verified commit · destination dirty · base drifted · conflicts · required tests not run/failed · implementation worktree dirty post-verification · (P4a W3-1) verification-runner violation (the primary checkout mutated during the implementor round's verification commands — agent-actionable blocker, §17.1). MVP reports exact manual integration commands (interpolated repoRoot/refs are POSIX shell-quoted so paths/refs with spaces or metacharacters stay copy-pasteable — W4-6); never executes them. Auto-commit-on-idle: config-gated, default off.
- **(P4a W2-2) Readiness blockers split by WHO can act**: agent-actionable (implementation worktree dirty post-verification, required tests, spec drift; mixed agent+user sets included) → T23 remediation, user blockers re-probed next round. User/environment-actionable ONLY (destination dirty · base drifted · conflicts) with all criteria verified → durable `merge.readiness.blocked {blockers, mergeReadiness}` supporting event + recheck read-model projection, run REMAINS `verifying`, NO remediation round consumed, CLI outcome `integration_blocked` (distinct exit code 4) printing the blockers + exact manual commands. `harness recheck RUN_ID` re-validates the worktree (§16.3 first, `worktreeClean` always re-probed) and re-runs ONLY the git probe against the SAME immutable Verification/binding: ready → ingest T24 now; still blocked → an updated blocked event. Wrong-commit (the tree moved under us) and a missing probe (caller bug — production always supplies it) are typed orchestration errors, never waitable blockers or T23 rounds.

## 17. Security, privacy, cost
### 17.1 Security
Minimal env allowlist for children (credentials only when the provider requires). **(P4a W3-1) Verification-runner confinement**: the host-run spec verification commands (implementor self-check) execute under the same minimal-allowlist discipline — `VERIFICATION_ENV_ALLOWLIST` (PATH + toolchain basics; NO credential-shaped vars; per-run additions only via explicit config `verification.envAllowlist`, credential-shaped names rejected; no blanket env inherit exists) — plus a primary-checkout mutation guard: HEAD, `git status --porcelain --ignored` (a NEW gitignored file is drift), a content manifest of the primary `.git/hooks` directory, and a hash of the primary `.git/config` are snapshotted before the commands and re-checked after (W3-1(b): hooks + config are the SHARED git common-dir a linked worktree also reaches, so planting `.git/hooks/pre-commit` or rewriting `.git/config` — even from the worktree cwd — is caught); any drift → typed `verification_runner_violation`, the round fails verification honestly, §16 readiness blocks, and a durable `verification.runner.violation` incident event is recorded. **(P4b W4-7) Timeout reaps the process TREE**: the default runner spawns each verification command `detached` in its OWN process group and, on timeout, drives the same graceful-then-forced ladder as the ACP transport (SIGTERM the group → 2s grace → SIGKILL the group; a final group SIGKILL sweeps stragglers the moment the shell exits) — so a command that started a background server/watcher cannot leave a detached descendant alive past the reported timeout (exit 124); `exec()`'s built-in timeout, which signals only the immediate shell, would have orphaned it. Documented residual: the guard covers exactly those dimensions, NOT the whole `.git` — non-code-execution internals (packed/loose refs, loose objects, `.git/info/*`) can still be mutated undetected (they are not persistence/RCE surfaces; the executable ones — hooks + config — ARE covered); reads/exfiltration without any mutation are also out of scope; no network confinement and no fs confinement beyond these guards in MVP; per-platform OS sandboxing (sandbox-exec / bwrap) is the roadmap item. Redaction before every sink (DB, artifacts, logs, checkpoints, memory, errors): auth headers, key formats, private keys, credential URLs, env assignments, project patterns. **(P4a W3-3) Metadata-sink redaction**: user-origin free text is redacted at the single event-append + projection-save boundary (the two repository methods every durable metadata row funnels through) via a REGISTERED field-level map — event `spec.revise.requested.feedback`; projections `run_meta.goal`, `spec_draft.goal` + `spec_draft.canonicalSpec` (plain `redactText`, converging byte-for-byte with the CAS spec artifact the approval hash binds — the CAS redacts before hashing), `role_round.inputs` (structural parse→per-leaf-redact→re-stringify so resume re-entry always parses valid JSON), `implement_verify_loop.taskScope` — never a blind deep-walk: enums/ids/hashes and unregistered payloads stay byte-identical, and replay folds the same redacted bytes the live path folded. Raw provider payloads stored only redacted + size-bounded. No prompts/secrets in paths. `doctor` checks adapter binary provenance (lockfile resolution incl. codex-acp optionalDependencies integrity). Grok Build opt-in only with incident note.
**Child-harness spawn isolation (normative; live-gate finding H-1)**: spawned harness cores must not inherit host-level config that weakens orchestrator permission mediation. Codex spawns use an isolated `CODEX_HOME` carrying auth material only (refresh-safe linkage, 0600 perms, contents never logged) plus orchestrator-owned config that routes approvals to the ACP client; `doctor` flags dangerous host config (e.g. `approvals_reviewer=auto_review`). Watch-list (non-blocking): Claude's SDK child inherits user-global MCP servers despite `mcpServers:[]` — promote `CLAUDE_CONFIG_DIR`-class isolation if it becomes load-bearing. Auth reporting (H-2): `supported` requires validated evidence (a recorded successful provider turn); bare key/credential presence reports as detected-but-unvalidated, never `supported`.
### 17.2 Cost accounting (honest)
Per-turn tokens/cost recorded from adapter `usageAccounting` where advertised; otherwise estimated with a conservative per-turn reservation before each turn. `--max-budget` is an **estimated soft budget**: new turns are refused when measured spend + estimated (reservation-folded) spend + reservation exceed it (`budget.exceeded` event) — estimated spend counts toward refusal; it is not claimed as a hard ceiling until an authoritative usage source exists. `status` shows total + per-role/per-phase attribution (the remediation loop must be visible as a cost center). Pricing tables versioned.
