## 1. User-locked scope
1. Usage-limit pause/resume is IN the MVP (flagship).
2. "Memory optimisation" = BOTH process supervision AND context/token economics.
3. The "Intent Next" design package is visual direction only (exception: limit-pause mechanics and the 8-state UI vocabulary).
4. Agent control on stdio; WebSockets only at the observation boundary. `harness serve` deferred post-MVP (review consensus).
5. Implementation runs via orchestrated workflows; all changes consolidated **unstaged** in the main workspace; merge/integration is never automated.

## 2. Problem statement
Coding-agent harnesses each own an agent loop (model calls, tools, permissions, context, native sessions) with different control surfaces and no portable session format. The product coordinates them without pretending they are interchangeable: goal → approved testable spec → isolated implementation → independent verification → merge-readiness; sessions that **pause on provider usage limits** (never respawn-loop), supervised processes (RSS watchdog, finite restarts, breaker, orphan reaping), full lineage (run/session/model/memory/evidence), model/harness changes only at safe boundaries, honest crash recovery, human in control of specs, permissions, integration.

## 3. Research conclusions (normative summary; evidence tiers in ORCHESTRATOR-NOTES §1)
- **ACP is the MVP control plane** for Claude Code + Codex via pinned official adapters (`@agentclientprotocol/sdk@1.2.1`, `claude-agent-acp@0.59.0`, `codex-acp@1.1.4`, Node ≥22.14). Adapters execute lockfile-pinned binaries only; codex-acp's platform binary arrives via lockfile-pinned `optionalDependencies`, no postinstall (verified — supply-chain concern resolved).
- **Precedent, stated precisely**: Intent by Augment v0.5.0 instantiates a single `ACPProvider` class for every interactive provider (claude-code, codex, opencode, pi, droid, cortex) after per-harness command resolution (`provider-registry.js:6-58,107`, re-verified locally). This proves feasibility of ACP-driving several harnesses; it does not prove portability, reliability, or market convergence. The SPI therefore keeps an executable non-ACP fallback seam (headless-JSON tier), not just a diagram box. No PTY tier: all 8 researched harnesses expose structured headless surfaces.
- **P2 compatibility gate (normative)**: before committing the rest of P2, run a live gate on both adapters covering permission mediation, cancellation, identity-confirmed resume, error-envelope visibility (incl. limit envelopes), and model-switch timeout/fallback. If the Claude adapter fails systemically (not anecdotally), the Claude Agent SDK adapter is promoted INTO the MVP as a correction. (Adapter risk anecdotes: switch flakiness #886, MCP injection loss #883, compaction invisibility #873, post-resolve updates #864 — treated as risks to gate, not settled facts.)
- **ACP has no rate-limit signaling** (closed StopReason enum: end_turn/max_tokens/max_turn_requests/refusal/cancelled). Claude adapter emits `-32603` + `data.errorKind='rate_limit'` (adapter convention, PR #582). Codex adapter emits `-32603` + `data.codexErrorInfo='usageLimitExceeded'` — a structured limit discriminator (source-verified in the pinned codex-acp@1.1.4 dist) with NO reset time; the richer RateLimitSnapshot telemetry (windows, resets_at) still never crosses ACP (#227 remains accurate for that signal). Classification design in §13 follows from this.
- **Model mechanisms are declarative per provider** (`modelMechanism`): current SDK = `session/set_config_option`; older deployments used `session/set_model`; others use env/CLI flags. Probe at initialize.
- Adapter roadmap after MVP: opencode (native `opencode acp`) → pi (in-process SDK / `--mode rpc`) → Droid/Auggie (native ACP; local installs stale — upgrade first) → Gemini. Grok Build: opt-in only (2026-07 privacy incident), never a default.
- Billing: API key is the documented path for Claude (third-party subscription OAuth barred by ToS 2026-02-19; billing-inconsistency issue #43333) and recommended for Codex automation. `doctor` reports auth per provider as `supported | detected_but_unsupported | unknown` — no categorical claims beyond evidence.
- SQLite: `node:sqlite` on Node 22.14.0 emits `ExperimentalWarning` (verified locally). Default driver = `better-sqlite3` behind the repository interface; the same contract tests run against `node:sqlite` to keep the swap live.

## 6. Domain model and state
### 6.1 Entities
`Run`, `SpecVersion` (immutable, content-hash), `Assignment` (role, spec hash, base commit, worktree, policy, wave/group id reserved), `SessionSegment` (one harness-native session; distinct ids: segment / ACP session / provider-native session / process-generation), `Turn`, `Event` (append-only, monotonic per-run sequence, idempotency keys), `Artifact` (content-addressed), `MemoryEntry` (§15), `Verification` (binds spec hash + base commit + implementation commit), `MergeReadiness`, `LimitIncident` (provider, limit kind, detection tier, resumes_at?, source, resolution), `ProcessSample` (aggregated projection; raw pruned), `Checkpoint` (§12.2).

### 6.2 State model — three orthogonal axes (no flat enum)
- **Run.phase** (workflow position): `created → specifying → awaiting_approval → approved → implementing → verifying → needs_remediation → implementing … → merge_ready` ; terminals: `cancelled`, `failed`. Supersession is not a Run.phase: modeled as `SpecVersion.status='superseded'` + `Assignment.status='stale'`; T3's `spec.superseded` event carries the follow-on phase (implemented in `src/domain/state.ts`, conformance-tested).
- **Assignment/Segment.suspension** (orthogonal, only while a child/segment is active or resumable): `none | paused_limit | paused_user | breaker_open | interrupted`. Suspension records `{reason detail, return_phase, in_flight_operation?, entered_at}`. Suspension never changes phase; resume returns to `return_phase`.
- **Segment.operation** (at most one in flight): `idle | prompt_turn | initial_config_pin | model_switch{from,to,requested_at} | checkpoint_write | git_op{kind} | resume_probe`. (P4a) `initial_config_pin` spans option discovery through §11.2 pin enforcement on a fresh spawn; `prompt_turn` only wraps actual prompt turns.
- **Active child is generation-tracked, never a boolean** (P4a): `activeChild {generationId, segmentId, status: spawning|active|stopping|stopped}`. `child.spawn.initiated` (P4a W2-3) marks the fresh generation `spawning` and opens the `initial_config_pin` window in the durable state; `child.spawned` (supporting event, carries role + pins incl. echo facts) is the only thing that marks a generation ACTIVE — appended strictly after pins succeed, closing the pin window; `turn.started`/`turn.completed` keep `operation=prompt_turn` truthful across prompt turns (so T4 is licensed on live ingest AND replay); pause/exit paths mark the generation `stopping` with a durable stop-intent (`child.stop.intent`); only a generation-MATCHED `child.stopped` confirms the stop — a late stop from generation N never clears N+1. Resume (T9/T12) records `resume_reentry_pending` (acked by `resume_reentry.completed`; startup/`resume` reclaim unacknowledged re-entries idempotently) and never marks a child active.
- **UI vocabulary is a projection**, never stored: Starting=spawn/handshake · Working=prompt_turn in implementing/verifying · Waiting on you=awaiting_approval or permission-wait · Paused—limit=paused_limit · Stopped=cancelled/paused_user · Done=merge_ready · Breaker open=breaker_open · Handed off=superseded-by-successor.

Produced by startup reaping (`reapOrphanProcesses`) for a dead-owner ACTIVE/`spawning` generation whose RoleRoundProjection stage is pending/active; a `completed` round is instead confirmed-stopped (no interrupt, no counter). Rules: approval binds the exact SpecVersion hash. Verification binds spec hash + base + implementation commit. `merge_ready` requires evidence for every criterion. Remediation bound (default 3) exhaustion → `failed`, never false completion. Every transition is one idempotent event append + projection update in one transaction. **(P4a W3-4) Coordinator-completion atomicity**: the `specifying → awaiting_approval` completion (`completeCoordinationRound`, shared by `start`/`spec revise`/the W2-5 coordinator re-entry) persists the spec-draft projection BEFORE the final workflow advance, both in ONE transaction, and the advance event carries the draft's `SpecDraftRef` (artifact hash == spec content hash + version + revision) — so replay can DETECT a lost/stale draft against the durable ref and `approve`/`run` refuse (`spec_draft_missing`/`spec_draft_stale`) with a recovery hint while `spec revise` re-drafts (rebuilding revision context from the completion ref + CAS artifact); a crash anywhere in the completion rolls back to `specifying` with the round re-drivable, never an approval-ready draftless run.

## 7. Specification contract
Coordinator returns a structured spec: goal; assumptions + unresolved questions; constraints + permissions; non-goals; ordered tasks + dependencies; acceptance criteria with stable IDs; verification commands + expected evidence; rollback/recovery notes; proposed implementor/verifier profiles (these become `run` defaults so `run` needs no profile args). Coordinator output is untrusted: schema-validated, ambiguous/untestable criteria rejected, stored immutable, human-approved — always. `spec revise` (T2) supports review→revise rounds. Imported human specs supported (still approved explicitly).

## 8. Role contracts (host-enforced; prompts follow the Augment template: frontmatter `{name, description, harness, model, roleReminder}`; body: Role → Hard Rules first → Workflow in order → Format spec → Tools → Completion report)
- **Coordinator**: read-only workspace; writes specs/exploration artifacts only; cannot approve own spec; cannot dispatch or mutate workflow state; `roleReminder` re-injected every turn.
- **Implementor**: writes only inside its assigned worktree; one approved spec version + bounded task scope; runs declared verification commands; returns changed files, diff, tests, exit statuses, risks, commit SHA; cannot change criteria or mark complete.
- **Verifier**: read-only on the exact implementation commit; maps every criterion ID to evidence it gathered itself (`passed | failed | unproven`; any failed/unproven blocks); the Coordinator's exploration artifact is available strictly as an **untrusted index bound to its source commit — never evidence**; structured fix-request output.
- Delegation depth ≤ 2, host-enforced. Harness-native subagent tools that conflict with orchestration are denylisted per profile (`conflictingBuiltinTools`).

## 9. Harness adapter SPI
Operations: `probe() · initialize() · createSession() · loadSession() · resumeSession?() · forkSession?() · prompt() · cancelTurn() · listConfigOptions() · setConfigOption() · resolvePermission() · classifyError(raw) · close()`.
- `resumeSession?` = native fast resume (no replay), returns `{resumed: 'native'|'replayed', identityConfirmed: boolean}`; `loadSession` = replay path. Conformance tests cover advertised-but-failed resume and identity mismatch. Native fork unused in MVP (successor lineage suffices); probed and recorded only.
- `classifyError` operates **only on adapter/protocol error envelopes** (JSON-RPC error responses, typed adapter errors, HTTP 429/Retry-After in API-key mode) → `{kind: usage_limit | auth | crash | protocol | unknown_provider_error, resumesAt?, source: structured|parsed, confidence}`. Free text inside agent messages is NEVER classified (a model merely *talking about* limits must not pause a run).
- Capability record: protocol+version, executable/package version, auth readiness (`supported|detected_but_unsupported|unknown`), create/load/resume/fork/cancel, model+mode+reasoning options, `modelMechanism`, permission-request support, MCP config support (report-only in MVP), checkpoint/export, `usageLimitReporting: structured|parseable|none`, `retryAfterTier: honored|forecast_fallback|forecast_only`, `usageAccounting: per_turn|none`, `conflictingBuiltinTools[]`, observed session identity. Unsupported capability → typed error; never silent degradation.

## 10. ACP transport (numeric limits normative)
### 10.1 Lifecycle
Resolve exact lockfile-pinned binary → spawn in own process group with identity nonce (`HARNESS_SPAWN_ID` env) → stdout exclusively ACP NDJSON; stderr retained bounded/redacted → initialize + capability probe (records fork/resume/config-option/mode support) → create/load session, confirm returned identity → prompts + normalized updates → cancel gracefully → escalate termination → close streams, reap process group (identity-verified, §14).
### 10.2 Limits and permissions
Handshake timeout 15s · turn timeout 30min · max protocol line 1MiB · decoded-event queue 1,000 (overflow = terminal event + cleanup) · stderr retention 64KiB head/tail · cancel grace 3s · terminate grace 2s. Malformed JSON, oversized lines, protocol mismatch, unexpected EOF → explicit terminal events. Permissions: interactive → surface ACP options to user; headless → deny unless assignment policy allowlists the exact operation; unknown → deny; Coordinator/Verifier writes always denied; no provider ever gets a global bypass flag. Turn boundary = `session/prompt` response; late `session/update` notifications are tolerated and attributed to the closed turn (never crash projections).

## 11. Session and model semantics
### 11.1 Resume
Persist separately: segment id, ACP session id, provider-native session id, process-generation id, last completed turn + event cursor. Resume in place only when the adapter advertises resume/load AND confirms the same session identity; prefer `resumeSession` (native) over `loadSession` (replay); any ambiguity → checkpoint-linked successor (the portable correctness path). (P4a W2-5) Run-level resume RE-ENTRY is driven entirely from the durable `RoleRoundProjection` (round, role, serialized inputs, spec/base binding, exact implementationCommit for verifier rounds, checkpoint ref, stage, intended completion advance) + the §12.2 checkpoint + the persisted loop binding/worktree facts — never from a dead process's memory. A transactional ELIGIBILITY check precedes EVERY T9/T12/interrupted re-entry (manual `resume` and the scheduled-probe T9 alike): assignment open + non-stale AND `checkpoint.specHash == assignment.specHash == engine approvedSpecHash == current draft.specHash`; any mismatch is a typed refusal WITHOUT clearing the suspension (a superseded spec can never resurrect an old round). Re-entry ADOPTS the assignment worktree via the manager (mutex + §16.3; never creates): an interrupted implementor gets WIP-commit-or-reset reconciliation (recorded durably); an interrupted verifier is forced back to the persisted implementationCommit with verifier dirt DISCARDED and clean asserted, restarting on the SAME immutable binding — checkpointed passed criteria carry over only with same-spec/commit-bound evidence, and `worktreeClean` is always re-probed after adoption. The re-entered round going ACTIVE acks the pending re-entry (`resume_reentry.completed`); startup/`resume` reclaim unacknowledged pending re-entries idempotently.
### 11.2 Model switching (only at confirmed completed-turn boundaries on a live session)
Discover options → validate against advertised values → persist `model.switch.requested` → invoke per `modelMechanism` → await effective-value echo → persist `model.switch.confirmed` | `failed`. Timeout (default 60s) + one retry, then checkpoint-successor. Cross-harness switch is always a successor: inject approved spec + selected memory + mechanical checkpoint + evidence refs; record that native continuity was not preserved. A limit during `requested` (T5) → `failed_indeterminate` → successor with explicit model re-assertion. Example: Codex terra drafts spec → user pauses at approval → switch to sol → confirmed in-session or checkpoint-successor → sol proposes spec v2.

## 12. Persistence, checkpoints, crash recovery
### 12.1 Store
`better-sqlite3` (D6 resolved; `node:sqlite` experimental on 22.14 — same contract tests keep the swap live) behind repository interfaces. WAL; foreign keys; busy timeout; migration table; restrictive permissions; one logical writer; transactions wrap event append + projection; monotonic per-run sequence; idempotency keys on provider notifications and transitions. Large payloads: redact → hash → content-addressed artifact dir; SQLite keeps metadata + bounded previews. **Quotas (normative)**: per-run artifact quota 2GB, global 20GB (admission rejection + event when exceeded); telemetry (vitals) aggregated per-minute in projections, raw samples pruned (the §14 watchdog sample path folds every CLOSED per-minute window and prunes the raw rows it folded, so `raw_process_samples` stays bounded to the in-progress window; `status` reads the newest closed aggregate and falls back to the latest raw tick for the still-open window so RSS is populated as soon as sampling starts); job/subscriber/wait queues bounded with drop-oldest+replay or dead-letter; reference-aware artifact GC.
### 12.2 Checkpoint contract (mechanical, synchronous, no LLM anywhere in the pause path)
Content: segment lineage (predecessor harness/model/session/final turn) · last completed turn id + event cursor · spec hash + per-criterion state · constraints + permission policy · confirmed decisions · unresolved risks · failing tests · artifact/evidence refs · exact worktree state (HEAD sha, `git status --porcelain` snapshot, diff hash, lockfile-cleanup performed?, taint flags) · `incomplete_operation?` (recorded honestly — a mid-turn checkpoint does NOT claim completed work). **Atomicity**: artifact written to CAS first, then `checkpoint.recorded` event with its hash in the same transaction as the state transition; artifact-without-event is invisible to replay and GC'd; event-without-artifact is impossible (event commits after artifact fsync). (P4a) The limit-pause path composes exactly this: `pauseForLimit` fsyncs the checkpoint artifact, then ONE atomic append carries the T4/T16 trigger + `checkpoint.recorded` + `limit.incident.recorded` + `child.stop.intent` (generation marked stopping); only then is the child cancelled/disposed, and the generation-matched `child.stopped` confirms — a restart at any crash point recovers idempotently (unreferenced artifact → GC'd; committed stop-intent without confirmation → identity-verified cleanup then `child.stopped`). A quota-rejected checkpoint write never blocks the pause: the run pauses without `checkpoint.recorded` (admission rejection recorded honestly). **Cadence**: every N completed turns (default 3) + before model switch, pause, verify handoff, graceful stop. (P4a W4-1) The completed-turn cadence is WIRED into the runtime: the service's role-session `prompt` boundary drives a per-run `CadenceTracker` (policy = `checkpoint.cadenceTurns`) that writes a `cadence` checkpoint (idle operation — a completed turn interrupts nothing) once N completed turns elapse; ANY checkpoint written (cadence or a safe-boundary pause/stop) resets the turn-count window so cadence never fires early. Narrative/LLM summaries are DEFERRED from MVP entirely; the mechanical core must be sufficient for successor context and is tested as such (§19-22).
### 12.3 Restart recovery
Never trust a stored PID alone; verify full process identity (§14) before any signal. Mark abandoned `running` work `interrupted` (T17); replay idempotent events to rebuild projections (this recovers ORCHESTRATOR state; the AGENT's in-context work is recovered only to the last checkpoint — the plan makes this distinction explicit); validate worktree (§16.3); resume confirmed session or checkpoint-successor. (P4a W4-4) `harness resume` also re-drives an UNSUSPENDED implementor/verifier run stranded at a role-completion boundary — the orchestrator died AFTER the round's `child.stopped` folded but BEFORE the next dispatch/verdict landed (implementor done → phase `implementing`; verifier round done → phase `verifying`, T23/T24 not yet applied). One `handleResume` dispatch gate (`suspension=none` ∧ round∈{implementor,verifier}/`completed` ∧ child stopped/absent ∧ phase non-terminal) routes it to `resolveResumeEntry`'s next durable step, GATED on §14 owner-liveness (`isRunClaimedByLiveProcess`) so a still-alive PEER's run is never double-driven. Implementor re-entry preserves partial WIP (§16.3 WIP-commit-or-reset); only the read-only verifier discards dirt. (P4a W4-4 residual) `isRunClaimedByLiveProcess` reads a durable RUN-ownership lease ({runId, ownerPid+start-time}) — NOT the per-child registry, whose record a clean child dispose removes: the lease is acquired at the outer entry of the implement/verify driver (both a fresh start-that-drives and a resume-that-drives) and released in its outer `finally`, so it is held ACROSS child rounds and survives the between-rounds child-dispose gap (implementor stopped, verifier not yet dispatched) where a live owner would otherwise hold no record — closing the last double-drive window. A lease whose owner pid is gone/recycled (§14 identity) does not claim the run and is reclaimed, so a crashed owner never blocks a legitimate resume. The SAME `isRunClaimedByLiveProcess` gate also guards the W3-4 coordinator re-drive carve-out AND the unacknowledged pending-re-entry carve-out, so EVERY resume re-drive path (coordinator, implementor, verifier, pending re-entry) is consistently owner-liveness gated. (P4a W4-2 Stage 1, review-6 F2) The lease is now EXCLUSIVE, not advisory: `acquire` is a COMPARE-AND-SWAP inside one `BEGIN IMMEDIATE` (the count-and-reserve shape) returning a BOOLEAN — it accepts iff the run is unclaimed, already self, or held by a provably dead/recycled owner (§14 liveness evaluated INSIDE the txn), so two concurrent reclaimers of one crashed run serialize on the write lock and the loser gets `false` (attack-e). The driver checks that boolean and WITHHOLDS (honest `RunOwnershipConflictError`, no double-drive) if it did not win, and acquisition happens BEFORE any worktree create/adopt or role work (not after). The lease is also extended to `runCoordination` (S4): a live coordinator round now holds it, so `isRunClaimedByLiveProcess` is TRUE during it (previously it acquired nothing, making the coordinator carve-out gate a production no-op).

## 13. Usage-limit pause/resume (flagship)
- **Detection**: `classifyError` on adapter error envelopes only (§9). Claude: `-32603` + `data.errorKind==='rate_limit'` → source=structured (conformance fixture pins this convention at adapter v0.59.0; startup probe verifies; version bump → re-characterization + loud downgrade). Codex: `-32603` + `data.codexErrorInfo==='usageLimitExceeded'` → source=structured, kind=usage_limit, ETA `unknown` (no reset field crosses ACP, #227) → probe ladder; envelope text patterns (parsed tier) remain corpus-gated; else `unknown_provider_error`. API-key mode: HTTP 429 + Retry-After → structured. **Evidence gate**: the parsed tier ships only after a reviewed corpus of real recorded limit transcripts per harness/version exists (P4a gate); until then only structured + unknown paths are active. Misclassification is fail-safe by construction: `unknown_provider_error` at the provider-call boundary pauses (T16) and never feeds the breaker.
- **Pause** (T4-T6): `pauseForLimit` — mechanical checkpoint fsynced to CAS first → ONE atomic append (trigger + `checkpoint.recorded` + `LimitIncident` + durable stop-intent) → graceful cancel/dispose → generation-matched `child.stopped` confirms the clean stop → notify (§12.2 composite append). Classification PRECEDES any retry: every provider-call failure (pin attempts AND prompt turns) is classified first — `usage_limit` pauses via T4 (through the in-flight operation, `initial_config_pin` or `prompt_turn`), `unknown_provider_error` pauses via T16 (never the breaker), auth/protocol takes the typed failure path, child-death takes T13; only a typed non-limit configuration rejection gets the single §11.2 pin retry. Role dispatch is pending/active split (P4a): the intended round persists `pending`, spawn+pin run at the previous stable phase, and the phase advances (round `active`, `child.spawned`) only after pins succeed — a non-limit pin failure leaves the pending round retryable. Never respawn on limit; respawn count stays 0.
- **Resume ETA**: structured `resumes_at` when present (source labeled `retry_after`); otherwise **`unknown` — honestly**: no invented countdown. Learned forecasting is deferred until real reset data is logged. Unknown-ETA schedule: bounded probe ladder 30m → 1h → 2h → 4h defaults, taken from the run's PINNED config (P4a: T10 only folds the probe count; the pure scheduler `src/scheduler/limit-schedule.ts` computes each deadline ANCHORED to event timestamps — incident/T10 times, never restart-relative — and records `limit.probe.scheduled {at, rung, probeIndex}`). Cap `maxProbesPerIncident` (default 6): exhaustion is **permanent per incident** (a sliding 24h window is deliberately rejected complexity); jitter deterministic from a (runId, probeIndex) hash. Probe = cheapest no-op turn on a fresh THROWAWAY session on the same profile pinned to the same model/effort as the role it would resume, executed behind a durable claim keyed (runId, incidentId, probeIndex) — the claim is the idempotency fence for the outcome, so concurrent waiters can never double-probe a rung or double-count T10. Probe outcomes: OK → T9 (mode `scheduled_probe`); limit envelope → T10 and the next rung; ANY other failure → durable `limit.probe.inconclusive {classifiedKind, detail}` — run stays paused, automatic probing STOPS (no T10, never the breaker), status surfaces it. Manual `resume` always available. (P4a W2-5) CLI policy: `run` (and `start`/`spec revise`, one shared LimitPausedError handler) on a limit pause WAITS by default — the schedule loop runs in-process on an injectable clock/timer and re-enters on T9; `--no-wait` exits code 3 with resume instructions; `resume` = eligibility check + immediate re-entry, `resume --wait` = the schedule loop; an elapsed structured retry_after re-enters as T9 mode `scheduled_probe` without consuming a probe. `status --json` while paused carries the limit block exactly: `{incident{provider, kind, source, confidence, at}, resumesAt: ISO|'unknown', etaSource: retry_after|unknown, probes{used, max, nextAt|null, inconclusive?}, policy}` — the word `unknown`, never an invented countdown.
- **Failover policy** per assignment (`wait | switch_model | switch_harness | ask`, default `wait`+notify): `switch_model` only between completed turns on a live session (§11.2), else successor; `switch_harness` = checkpoint-successor on alternate provider; mid-turn limit → successor always (T5/T6); all targets limited → T25 `failover_exhausted`, stay paused, notify. **(P4a W4-1)** Only `wait` is IMPLEMENTED (runtime + status honestly report `wait`); the non-`wait` policies are P4b. Config binding therefore REJECTS any non-`wait` `failoverPolicy` at parse with a clear "not yet supported (P4b)" error rather than silently accepting a no-op override — an accepted config must act or be refused.

## 14. Process supervision
- **Identity**: registry persists {pid, pgid, process start-time, executable path, generation id, `HARNESS_SPAWN_ID` nonce, **owning-orchestrator pid + start-time**}. Any signal (watchdog, reaper, cancel) requires full identity re-verification; ambiguity → never kill, surface an alert. Startup reaping kills only identity-verified orphans. (P4a W4-0) Reaping is additionally OWNER-GATED: `reapOrphans` skips — never verifies, signals, or removes — any record whose OWNING orchestrator is still alive (self, or a live PEER, via the same owner-liveness check as the spawn-reservation store: `isAlive(ownerPid)` + start-time match, recycled-pid safe), reaping ONLY records whose owner is provably dead (or a recycled owner pid, or absent = legacy/unowned). This closes a pre-existing peer-kill bug where a `resume` in one process SIGKILLed a DIFFERENT live orchestrator's identity-unambiguous child (the withhold-on-ambiguity guard does NOT cover an unambiguous live peer). The owner pid is stamped = the registry's `#selfPid` at registration. (P4a W2-6) The identity is captured at the `RoleAdapterHandle` right after spawn, the registry store is DURABLE (backed by the existing SQLite projection layer), and the record is persisted BEFORE `child.spawned` commits — a crash anywhere after the OS process exists leaves a reapable record. Startup reaping (run at `resume`) additionally re-verifies the nonce by reading the child's env where the platform allows (darwin/linux best-effort): a contradicting or unreadable nonce WITHHOLDS the signal and surfaces a durable `process.identity.alert` event; a provably-GONE generation completes any committed stop-intent (`child.stopped` reason `startup_cleanup`, §12.2). (P4a W3-2) CROSS-PROCESS control: a `pause`/`cancel` issued from a SECOND CLI process only appends the intent — the live child runs in the FIRST process — so after the append the intent's owner routes the stop through this same durable registry (`stopExternalChild`): the FULL §14 identity (ps identity AND the env nonce) is re-verified and a signal is delivered to the child's process GROUP, WITHHELD+alerted on any ambiguity (never signal a recycled pid). `pause` sends one graceful SIGTERM; `cancel` escalates the §10.2 terminate ladder (SIGTERM → terminate grace → identity-verified SIGKILL, re-verified before each rung). The owning process observes the death through its transport and folds the generation-matched `child.stopped` (the existing runRole/T13 fold). A generation still live IN the acting process is left to the in-process stop path (limit pause, run-owned cancel) — never cross-signaled.
- **Watchdog**: RSS of full process tree sampled 5s adaptive → aggregated projection. Budget default 1024MB — taken from the run's PINNED config (W1-F5), not the driving process's: soft 75% → warn event + notify (T21 through the service); 100% → graceful path (mechanical checkpoint reason `pre_graceful_stop` + cancel/dispose stop ladder) under deadline (default 30s); hard emergency ceiling (default 150% of budget) → immediate identity-verified SIGKILL → worktree TAINTED (§16.3) via the attached manager. The subsequent child death reaches T13 through the same provider-failure classification path as every child death (one producer). Watchdog termination **participates in the worktree mutex**: while a segment holds a git-op lease, kill waits for op completion or the emergency ceiling (which taints). Watchers are deregistered on every dispose path. (P4a W4-5) A background sample tick that THROWS (a `ps`/`execFile` blow-up, distinct from the routine "process gone" outcome) is caught by the scheduler — never allowed to become an unhandled rejection that could crash the host or silently kill supervision — surfaced via a durable `onSupervisionFailure` alert, and the next sample is rescheduled (fail-open-with-alert). (P4a W4-5) The `ps` process-group/RSS adapter is **macOS-only** in the MVP (BSD/macOS flags); `package.json` declares `"os": ["darwin"]`, `doctor` warns on a non-darwin host, and a GNU/Linux `ps` adapter is roadmap.
- **Restarts/breaker**: window bound (default 5/10min, configurable 3|5|8) AND non-disableable per-assignment lifetime cap (default 10) AND no-progress detection (identical checkpoint content-hash across 2 consecutive restarts → breaker). `off` exists only behind an explicit `--unsafe-dev` flag and retains the lifetime cap. Exponential backoff between restarts; max elapsed recovery time (default 30min) → breaker. Limit-pauses never count (T4/T16). (P4a W4-1) The `RestartBreaker` is WIRED into the runtime CHILD-crash site (`#interruptOnChildDeath`) — its sole caller; it consumes the durable lifetime counter (never re-tracked in-memory) plus its own time-decayed restart window keyed per assignment (run-id fallback for assignment-less spawns), and `breaker reset` (T15) clears that in-memory window alongside the durable counters. Orchestrator restarts (T17) are deliberately NOT routed through it.
- **Concurrency**: simple max-live-children guard (default 3) — the MVP is serial-per-run; RAM-tier scheduling + LRU eviction deferred to the parallel-waves phase (and then derived from available memory + measured per-process reservation, not copied constants). (P4a W3-5) The guard is wired into `runRole`'s spawn path: admission is refused (`MaxLiveChildrenExceededError`, before any spawn) at capacity, and the cap is GLOBAL across concurrent CLI processes. (P4a W4-8) Admission runs BEFORE anything durable OR any provider resource is created — ahead of the pending-round save AND ahead of `#adapterFactory.create` (which for the Codex path prepares the §17.1 H-1 isolated `CODEX_HOME` at creation time) — so a cap refusal leaks neither a durable pending round nor a temp `CODEX_HOME`; a resource-setup failure AFTER admission releases the durable reservation + in-process slot before propagating. (P4a W3-5a) The count-and-reserve is ATOMIC across processes: each process reserves a durable spawn slot (a reservation record written BEFORE the spawn) inside a single serialized `BEGIN IMMEDIATE` write transaction that also counts identity-alive live slots — so two processes started concurrently serialize on the write lock and the N+1th observes the prior reservation, instead of both reading zero (the registry record alone lands only at `child.spawned`, leaving a TOCTOU window). A crashed peer's reservation (owner pid gone/recycled, §14 identity) is excluded and reclaimed, never holding capacity hostage or deadlocking; the slot is released on every `runRole` exit path. (P4a W4-4) A sibling durable store keyed by RUN (not generation) records a RUN-ownership lease ({runId, ownerPid + start-time}) — the owner/control channel — acquired for the WHOLE time a process actively drives a run (the implement/verify driver's outer entry, held across child rounds) and released in its outer `finally`; the consumer resume gates consult it (`isRunClaimedByLiveProcess`) so a between-rounds gap — where a clean child dispose has removed the per-child registry record but the owner is still alive — cannot let a concurrent `resume` double-drive the worktree. Same owner-liveness rule: a lease from a dead/recycled owner does not claim the run and is reclaimed (crash recovery, no deadlock). (P4a W4-2 Stage 1, review-6 F2) This lease is EXCLUSIVE: like the count-and-reserve, `acquire` is a compare-and-swap in one `BEGIN IMMEDIATE` returning a boolean (accept iff unclaimed/self/dead-owner), acquired BEFORE any worktree work; the driver refuses to drive (withholds) when it loses the swap to a still-live peer, and `runCoordination` holds the same lease so a live coordinator round is genuinely claimed (S4).
- **Self-supervision**: the orchestrator bounds its own memory (stream artifacts to CAS, bounded queues/projections per §12.1) and emits a heartbeat event (60s) so a stall is observable.

## 16. Git worktrees and merge-readiness
1. Require a git repo; resolve immutable base SHA. 2. Dedicated branch + worktree outside the primary checkout. 3. Single-writer lease per assignment. 4. Implementor confined to its worktree. 5. Record diff, tests, resulting commit. 6. Verifier inspects that exact commit read-only. 7. `MergeReadiness` only for the verified commit.
- **16.2 Mutex**: all `git worktree add/remove` serialized per repo (concurrent ops corrupt `.git/worktrees`). The supervisor's kill path respects git-op leases (§14). (P4a W3-5) The in-process `GitOpMutex` is complemented by a CROSS-PROCESS file-based advisory lease (a lock dir under the primary repo's `.git`, atomic `mkdir` gate) held around `worktree add/remove` — so a SECOND `harness` OS process on the same repo cannot race the git op; a lease held by a dead/recycled pid is reclaimed via §14 identity (pid + start-time), never waited on. (P4a W3-5d) A HOLDERLESS orphan (lock dir present but its identity file missing/unreadable/malformed — a process that crashed in the mkdir→stamp window or left a corrupt file) is likewise reclaimed after a bounded grace, never a permanent deadlock; the grace is long enough that a live acquirer mid-stamp is never falsely reclaimed.
- **16.3 Taint + validation**: emergency kills or deadline terminations mark the worktree TAINTED. Before any restart or verification on a worktree: remove stale `index.lock` (within the mutex), parse `git status`, verify HEAD readable, reconcile against the last checkpoint's recorded worktree state (dirty/partial → WIP-commit or reset-and-record; refusal to resume-in-place on mismatch). This runs before the lease releases at pause/kill time. (P4a W2-5) The WIP-commit path is the IMPLEMENTOR's reconciliation; an interrupted VERIFIER round is instead forced back to its persisted implementationCommit with verifier-created dirt DISCARDED (mutex-protected `discardToCommit`: stale-lock cleanup, hard reset, untracked clean, clean asserted) — a read-only verifier's evidence dirt is never preserved work.
- Readiness fails if: any criterion failed/unproven · spec hash changed · implementation commit ≠ verified commit · destination dirty · base drifted · conflicts · required tests not run/failed · implementation worktree dirty post-verification · (P4a W3-1) verification-runner violation (the primary checkout mutated during the implementor round's verification commands — agent-actionable blocker, §17.1). MVP reports exact manual integration commands (interpolated repoRoot/refs are POSIX shell-quoted so paths/refs with spaces or metacharacters stay copy-pasteable — W4-6); never executes them. Auto-commit-on-idle: config-gated, default off.
- **(P4a W2-2) Readiness blockers split by WHO can act**: agent-actionable (implementation worktree dirty post-verification, required tests, spec drift; mixed agent+user sets included) → T23 remediation, user blockers re-probed next round. User/environment-actionable ONLY (destination dirty · base drifted · conflicts) with all criteria verified → durable `merge.readiness.blocked {blockers, mergeReadiness}` supporting event + recheck read-model projection, run REMAINS `verifying`, NO remediation round consumed, CLI outcome `integration_blocked` (distinct exit code 4) printing the blockers + exact manual commands. `harness recheck RUN_ID` re-validates the worktree (§16.3 first, `worktreeClean` always re-probed) and re-runs ONLY the git probe against the SAME immutable Verification/binding: ready → ingest T24 now; still blocked → an updated blocked event. Wrong-commit (the tree moved under us) and a missing probe (caller bug — production always supplies it) are typed orchestration errors, never waitable blockers or T23 rounds.

## 17. Security, privacy, cost
### 17.1 Security
Minimal env allowlist for children (credentials only when the provider requires). **(P4a W3-1) Verification-runner confinement**: the host-run spec verification commands (implementor self-check) execute under the same minimal-allowlist discipline — `VERIFICATION_ENV_ALLOWLIST` (PATH + toolchain basics; NO credential-shaped vars; per-run additions only via explicit config `verification.envAllowlist`, credential-shaped names rejected; no blanket env inherit exists) — plus a primary-checkout mutation guard: HEAD, `git status --porcelain --ignored` (a NEW gitignored file is drift), a content manifest of the primary `.git/hooks` directory, and a hash of the primary `.git/config` are snapshotted before the commands and re-checked after (W3-1(b): hooks + config are the SHARED git common-dir a linked worktree also reaches, so planting `.git/hooks/pre-commit` or rewriting `.git/config` — even from the worktree cwd — is caught); any drift → typed `verification_runner_violation`, the round fails verification honestly, §16 readiness blocks, and a durable `verification.runner.violation` incident event is recorded. **(P4b W4-7) Timeout reaps the process TREE**: the default runner spawns each verification command `detached` in its OWN process group and, on timeout, drives the same graceful-then-forced ladder as the ACP transport (SIGTERM the group → 2s grace → SIGKILL the group; a final group SIGKILL sweeps stragglers the moment the shell exits) — so a command that started a background server/watcher cannot leave a detached descendant alive past the reported timeout (exit 124); `exec()`'s built-in timeout, which signals only the immediate shell, would have orphaned it. Documented residual: the guard covers exactly those dimensions, NOT the whole `.git` — non-code-execution internals (packed/loose refs, loose objects, `.git/info/*`) can still be mutated undetected (they are not persistence/RCE surfaces; the executable ones — hooks + config — ARE covered); reads/exfiltration without any mutation are also out of scope; no network confinement and no fs confinement beyond these guards in MVP; per-platform OS sandboxing (sandbox-exec / bwrap) is the roadmap item. Redaction before every sink (DB, artifacts, logs, checkpoints, memory, errors): auth headers, key formats, private keys, credential URLs, env assignments, project patterns. **(P4a W3-3) Metadata-sink redaction**: user-origin free text is redacted at the single event-append + projection-save boundary (the two repository methods every durable metadata row funnels through) via a REGISTERED field-level map — event `spec.revise.requested.feedback`; projections `run_meta.goal`, `spec_draft.goal` + `spec_draft.canonicalSpec` (plain `redactText`, converging byte-for-byte with the CAS spec artifact the approval hash binds — the CAS redacts before hashing), `role_round.inputs` (structural parse→per-leaf-redact→re-stringify so resume re-entry always parses valid JSON), `implement_verify_loop.taskScope` — never a blind deep-walk: enums/ids/hashes and unregistered payloads stay byte-identical, and replay folds the same redacted bytes the live path folded. Raw provider payloads stored only redacted + size-bounded. No prompts/secrets in paths. `doctor` checks adapter binary provenance (lockfile resolution incl. codex-acp optionalDependencies integrity). Grok Build opt-in only with incident note.
**Child-harness spawn isolation (normative; live-gate finding H-1)**: spawned harness cores must not inherit host-level config that weakens orchestrator permission mediation. Codex spawns use an isolated `CODEX_HOME` carrying auth material only (refresh-safe linkage, 0600 perms, contents never logged) plus orchestrator-owned config that routes approvals to the ACP client; `doctor` flags dangerous host config (e.g. `approvals_reviewer=auto_review`). Watch-list (non-blocking): Claude's SDK child inherits user-global MCP servers despite `mcpServers:[]` — promote `CLAUDE_CONFIG_DIR`-class isolation if it becomes load-bearing. Auth reporting (H-2): `supported` requires validated evidence (a recorded successful provider turn); bare key/credential presence reports as detected-but-unvalidated, never `supported`.
### 17.2 Cost accounting (honest)
