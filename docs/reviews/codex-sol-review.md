# Adversarial review of PLAN.md Rev 2

This review is grounded only in `PLAN.md`, `docs/ORCHESTRATOR-NOTES.md`, and `docs/archive/PLAN-v1-codex.md`. Verdicts, severity rankings, cuts, and recommendations below are judgments; failure scenarios are hypothetical consequences of the cited text.

## Debate-item verdicts

**(a) Claude transport — use ACP-uniform for the MVP, conditionally.** Rev 2's reason for one transport is sound at MVP scale: one conformance suite, permission path, and process lifecycle, while the stronger Claude SDK features are not required by the stated vertical slice (notes §2, D-transport; PLAN §§3.2, 4.1). This also preserves Rev 1 §§3.2 and 4.1. The condition is an early Claude ACP compatibility gate covering permission mediation, cancellation, identity-confirmed resume, error-envelope visibility, and model-switch timeout/fallback. If that gate exposes systemic rather than anecdotal adapter failure, the Claude SDK becomes an MVP correction, not an automatic fast-follow. The notes explicitly say the magnitude of #886 is unknown (notes §§1 and 3); the plan must not decide this from an issue anecdote alone.

**(b) Strategic ACP bet — use ACP as the primary control plane, not as an irreversible product assumption.** Intent's extracted implementation is direct evidence that ACP can drive several harnesses, but it is one locally inspected, scout-reported implementation, and the notes say giant files were only grepped (notes §1). It proves feasibility, not portability, reliability, or market convergence. Keep the transport-agnostic SPI and a structured headless/native-RPC fallback contract from day one (PLAN §§3.1, 5, 9; Rev 1 §§3.1, 4.2, 5). Do not build a PTY tier in the MVP: the documents report structured headless surfaces for all eight harnesses and identify no MVP-only capability requiring a terminal emulator (PLAN §3.1; notes §2, D-transport). Headless-JSON-everywhere was not dismissed frivolously—Codex permission and session semantics remain an identified deficit—but it should remain an executable fallback, not merely a diagram seam.

**(c) WebSockets — approve only at the observation boundary; defer `serve`.** Stdio correctly owns child lifecycle and agent control, while a subscriber can replay persisted events by sequence (PLAN §1, item 4, and §§5 and 18; notes §2, D-WS). In my judgment, `harness serve` should follow the MVP because the plan has not specified subscriber backpressure, cursor scope, disconnect recovery, Origin checks, or how a slow observer is prevented from blocking the single writer. Deferral preserves the boundary without adding a second externally reachable surface.

**(d) Fork/resume — capability-probe, but make checkpoint-successor the correctness path.** Advertised native resume is a worthwhile optimization only after same-identity confirmation; that requirement is retained in PLAN §11.1 from Rev 1 §11.1. Probe and record fork/resume support, use resume only under that invariant, and fall back on any ambiguity. Do not use native fork in the MVP unless a concrete workflow requires it: the notes say the required/optional method boundary may shift (notes §3, item 6), while the MVP already has successor lineage. PLAN §9 must first add an explicit `resumeSession?` operation or state that `loadSession` owns native resume; currently §11.1 prefers `session/resume` but the SPI lists only `loadSession` plus `forkSession?`.

**(e) MCP passthrough — defer session injection entirely.** Capability discovery may be reported by `doctor`, but no MVP workflow should pass MCP servers into a session. PLAN §§3.3 and 4.2 say tool visibility can silently fail and MCP is off the critical path; best-effort injection would therefore add a second meaning of “supported” while §9 says unsupported capabilities must never silently degrade. Revisit only with a post-create visibility attestation that the target model actually sees the expected tools.

**(f) D7 `--quick` — reject the proposed form.** Auto-approval contradicts explicit human approval in PLAN §§4.1, 6.1, 7 and Rev 1 §§1, 6.2, 7. The “single combined implement+verify pass” separately contradicts independent verification in PLAN §§4.1, 8, 16 and Rev 1 §§4.1 and 8. A size/risk heuristic is not specified or testable, and “always-overridable” does not restore approval that was skipped (PLAN §21 D7; notes §2, D-scope/ceremony). A later quick mode may shorten spec generation and defaults, but it must still require an approval action and a separate verifier identity against the exact commit.

**(g) Memory design — overbuilt and internally inconsistent for this MVP.** Keep Rev 1's immutable artifacts, verbatim handoff core, provenance, deterministic selection, and token/character budget (Rev 1 §13; PLAN §15). Defer bi-temporal semantics, global memory, and the LLM summarizing compactor. PLAN §15 calls `MemoryEntry` ADD-only and then says `invalidated_at` is set, which is an in-place update unless invalidation is a separate append-only record. Notes §2, D-memory concedes one implementor, no evidence-based budget values, and an LLM call that must not block pause. If invalidation is retained, model it as an immutable invalidation edge/event with explicit query-time semantics and project/tenant boundaries; do not label a mutable timestamp ADD-only.

## Open-decision rulings

**D1:** ACP-uniform, subject to the P2 compatibility gate described under (a). A failed gate promotes the Claude SDK to MVP scope (PLAN §21 D1; notes §2, D-transport).

**D2:** Support API-key authentication as the documented MVP path, but do not turn the documents' uncertainty into a categorical Codex subscription claim. PLAN §17 recommends API keys; notes §§1 and 3 say the ToS facts are scout-reported and Codex subscription headless usability is unconfirmed. `doctor` should report supported, detected-but-unsupported, and unknown auth modes separately.

**D3:** Do not hard-code a default coordinator model from the terra/sol example. The three sources provide an example flow but no comparative evidence for quality, cost, availability, or model longevity (PLAN §§11.2, 21 D3; Rev 1 §11.2). Require an explicit configured profile, allow the harness default only when capability discovery confirms it, and choose a product default after the live compatibility gate.

**D4:** Defer `harness serve`; retain the internal subscriber contract and deterministic replay test only if it does not require a network server (PLAN §§4.1, 18, 19, 21 D4).

**D5:** Defer MCP session injection; capability reporting only, as ruled in (e) (PLAN §§3.3, 4.2, 21 D5).

**D6:** Run the promised time-boxed P1 driver spike and select the driver by the same repository contract tests. The sources explicitly leave `node:sqlite` maturity open and already provide a `better-sqlite3` fallback (PLAN §§12, 21 D6; notes §3, item 3). There is no textual basis here for preselecting either one.

**D7:** Defer/reject the proposed auto-approval and combined-verifier mode, as ruled in (f) (PLAN §21 D7).

## Ranked flaw list

Severity and rank are my judgment. Each scenario states a concrete way the cited gap can fail.

1. **High — the run state machine is not executable as specified (PLAN §§6.1, 12, 13, 18; notes §2, D-states).** `paused_limit` is reachable from “any active state,” but the notes narrow the intended set to specifying/implementing/verifying and explicitly leave `awaiting_approval` and model-switch confirmation unresolved. No field preserves the return phase. `breaker_open` requires manual reset, but §6.1 gives no reset transition and §18 has no reset command; `harness pause` has no `paused_user` state; `interrupted` has recovery prose in §12 but no outgoing arc. Permission-wait is a UI label, not a canonical state. **Scenario:** a late adapter update reports a limit after the coordinator prompt has resolved and the run is awaiting approval; the run enters `paused_limit`, then scheduled resume has no defined target and may rerun the coordinator or bypass approval. **Fix:** model workflow phase, suspension reason, and in-flight operation as orthogonal state; persist `return_phase`/operation identity; enumerate every legal command and event transition, including approval, permission wait, checkpoint, model-switch requested/confirmed, user pause, breaker reset, cancellation, and recovery; generate transition tests from that table.

2. **High — watchdog and orphan cleanup can damage the worktree or an unrelated process (PLAN §§12, 14, 16; Rev 1 §12; notes §2, D-supervision).** The notes admit checkpoint-at-100%-RSS may be impossible and termination during a git write can corrupt the worktree. The worktree mutex covers only add/remove. Separately, startup orphan reaping says to kill a persisted pgid, while retained Rev 1 recovery says never trust a stored PID alone; a pgid is also a reusable OS identifier. **Scenario:** the watchdog escalates while `git update-index` is writing, leaves an index lock or partial index, restarts the implementor, and later verification reasons over a damaged tree. After another reboot, a stale pgid belongs to an unrelated process group and the reaper kills it. **Fix:** persist and verify process start identity, executable, parent/ownership marker, generation, and pgid before signaling; never kill when identity is ambiguous. Add periodic safe-point checkpoints, a hard emergency threshold, graceful deadline, “worktree tainted” state, and mandatory repository/index/commit validation before restart or verification.

3. **High — “checkpoint covers all work” is not achievable at the failure points the plan permits (PLAN §§13–15; Rev 1 §§11.2, 13; notes §2, D-supervision and D-memory).** A provider limit or RSS breach can occur mid-turn or mid-tool write. The child may be unable to produce more context, and the notes say an LLM summary must not block pause. PLAN §13 nevertheless makes checkpoint-first a prerequisite, stops the child, and allows `switch_model` through the in-session §11.2 flow; retained Rev 1 §11.2 permits switches only between completed turns. **Scenario:** a limit lands during a file write, the incomplete turn has no final response, summary consolidation is pending, the process is stopped, and an in-place switch is attempted against the stopped/limited session. The resulting checkpoint cannot honestly claim all work or a safe model boundary. **Fix:** define a synchronous mechanical checkpoint that records last completed turn, event cursor, exact worktree status/diff, artifact hashes, and an explicit `incomplete_operation`; make narrative summary optional asynchronous enrichment. On a mid-turn limit, use a checkpoint-linked successor by default and never claim native continuity. Permit in-session switching only at a confirmed completed-turn boundary on a live session.

4. **High — “bounded restarts” are only rate-limited and can be disabled (PLAN §§2, 6.1, 14).** The plan promises no respawn loops, yet `3|5|8|off` permits no breaker, and even four restarts every ten-minute window can continue for the run's lifetime. **Scenario:** a deterministic adapter crash occurs once every three minutes; the count never exceeds five in a moving window, so the run respawns indefinitely, accumulating events, artifacts, cost, and process churn. **Fix:** enforce both a non-disableable per-window bound and a finite per-assignment/per-run total, with exponential backoff, maximum elapsed recovery time, and terminal/manual intervention. If `off` exists for development, require an explicit unsafe flag and retain an outer hard bound.

5. **High if adopted — D7 breaks two safety invariants, not one (PLAN §§4.1, 7, 8, 16, 21 D7; Rev 1 §§1, 7, 8; notes §2, D-scope/ceremony).** **Scenario:** a task appears small by line count but changes an authorization default; the heuristic auto-approves it and the same combined actor implements and “verifies” its own mistaken criterion. **Fix:** defer D7. A future fast path may use a bounded template and one-click approval, but approval remains explicit and verification remains a separate role/session against the exact commit.

6. **Medium — the adapter contract cannot express the preferred native resume path (PLAN §§6, 9, 11.1).** The capability record has `resumeSupport`, and §11.1 prefers `session/resume`, but §9 adds only `forkSession?` to the Rev 1 operation list. **Scenario:** probing reports native resume, yet the application can call only `loadSession`; adapters either overload that method differently or silently drop to replay, defeating typed capability semantics. **Fix:** add `resumeSession?` with identity/result semantics, or normatively define `loadSession` as the single operation that selects native resume versus replay and reports which occurred. Add conformance tests for advertised-but-failed resume and identity mismatch.

7. **Medium — limit classification and ETA forecasting lack an empirical correctness boundary (PLAN §§3.3, 13, 19, 20; notes §2, D-flagship detection, and §3, items 1 and 5).** Recorded error strings do not yet exist, Codex structured crossing is absent, forecast history may be empty, backoff/jitter are unspecified, and notes say forecasts may be wrong by hours and probes can re-trip a limit. Synthetic window-fit tests prove the implementation matches its synthetic model; they cannot prove provider reset accuracy. **Scenario:** ordinary model text includes a limit-like phrase or a cold-start window model invents an ETA; a healthy run pauses, or a scheduled “no-op” turn burns quota repeatedly. **Fix:** classify only adapter error envelopes, version classifiers by harness version, use `unknown` ETA on cold start or low confidence, bound probe count/backoff, and require a reviewed real-transcript corpus before the P4 gate. Deterministic tests should assert parser behavior, timer/backoff invariants, and honest source/confidence labels—not real-world forecast accuracy.

8. **Medium — recurring and append-only data paths have no aggregate bounds (PLAN §§6, 12, 14, 15).** Process samples are a pruned ring projection, but §14 also emits usage-style events; the authoritative event log, content-addressed checkpoints/artifacts, ADD-only memory, wait queue, and asynchronous summary work have no retention, disk quota, admission limit, or retry bound. **Scenario:** a long paused/restarting run emits vitals and checkpoint artifacts while summary jobs lag; SQLite and artifact storage grow until disk exhaustion, while a burst of runs grows the wait queue in memory. **Fix:** keep workflow/audit events append-only but aggregate or rate-limit telemetry; define per-run/global disk and artifact quotas, bounded subscriber/job/wait queues, admission rejection, job retry/dead-letter rules, and reference-aware artifact garbage collection.

9. **Medium — memory invalidation is internally contradictory and cross-scope isolation is undefined (PLAN §15; Rev 1 §13; notes §2, D-memory).** “ADD-only” conflicts with setting `invalidated_at`; “bi-temporal” is named without valid-time/transaction-time fields or selection rules; `global` scope has no project/user/tenant boundary in the three documents. **Scenario:** two later facts contradict one entry; concurrent invalidations mutate the same row, and a selector either includes stale content or exposes global content in another project. **Fix:** retain Rev 1's creation/expiry and deterministic selection for MVP. If invalidation is essential, append immutable invalidation/supersession edges, define conflict authority and as-of queries, and make project/owner namespace mandatory; defer global scope.

10. **Medium — the shared exploration optimization can weaken verifier independence (PLAN §§8, 15, 16; Rev 1 §§8.3, 14).** PLAN §15 says the Coordinator's artifact is injected into the Verifier so the repo is not read three times, while §§8 and 16 require independent criterion evidence against the exact implementation commit. In my judgment, the artifact is useful only as an untrusted index. **Scenario:** the Coordinator explored the base commit and missed a generated configuration path changed by the Implementor; the Verifier relies on the injected summary and never inspects the changed surface. **Fix:** bind exploration artifacts to a source commit and label them non-evidence; require the Verifier to inspect the exact verified commit and independently execute/read whatever each criterion requires.

11. **Medium — the claimed hard cost ceiling has no specified authoritative input (PLAN §§6, 9, 14, 17, 19).** §17 says `--max-budget` is enforced from event-log accounting, but the domain/capability records specify limit reporting, RSS, context, and model mechanisms—not a guaranteed usage/cost source, pricing version, reservation, or unknown-usage policy. **Scenario:** an adapter emits no token accounting and a long turn crosses the ceiling before the next event. **Fix:** advertise usage-accounting capability, version prices, reserve a conservative maximum before a turn, and define behavior for unknown usage. Until then call it an estimated soft budget, not an enforced ceiling; test arithmetic and refusal policy deterministically.

12. **Medium if `serve` ships — observation backpressure and local-web security are unspecified (PLAN §§5, 12, 18, 19).** Token authentication and replay-by-sequence do not define loopback binding, Origin policy, cursor as `(run_id, sequence)`, per-subscriber queue bounds, or isolation from the one logical SQLite writer. **Scenario:** a disconnected or slow WebSocket client retains events faster than it drains them, consuming memory or delaying projection writes; a local hostile page attempts to attach to the service. **Fix:** defer D4, then specify loopback-only binding, random scoped tokens, Origin validation, bounded drop-and-replay subscriber queues, cursor scope, and read-only subscriber isolation.

13. **Medium — single-source implementation observations are treated as portable operating defaults (PLAN §§3.4, 14; notes §§1 and 2, D-supervision).** The notes call Augment's exact RAM tiers “production-tested,” but the evidence log describes a scout's local asar inspection, not workload telemetry or validation for this process model. The tier table also stops at `≤64GB`, and LRU eviction assumes reliable resume that the same notes call uncertain for Codex. **Scenario:** a 64GB host admits 30 agents based on total rather than available memory, evicts a session that cannot cheaply resume, and enters churn under memory pressure. **Fix:** treat the tiers as provisional configuration, derive admission from available memory plus measured per-process reservation, specify the >64GB case and queue fairness, protect permission/in-flight sessions from eviction, and require a durable checkpoint plus verified resume capability before eviction.

14. **Low — Rev 2 is not self-contained despite being labeled consolidated (PLAN §§6–12, 16, 19).** Normative behavior is repeatedly expressed as “as Rev 1” or “retained,” including the nineteen baseline tests and exact transport limits (Rev 1 §§10.2, 17.1). **Scenario:** an implementor follows only PLAN.md and misses a numeric queue limit or one of the inherited recovery tests. **Fix:** inline every normative retained rule/test into Rev 2, or declare the archived revision a versioned normative dependency with an explicit hash and amendment precedence. A consolidated implementation plan should preferably do the former.

## Rev 1 defenses and Rev 2 amendments

The Rev 2 amendments worth retaining are the user-locked limit-pause feature as a first-class incident rather than a generic crash (PLAN §§1, 6, 13); the per-repo worktree add/remove mutex (PLAN §§3.4, 16); adapter-binary provenance checks and lockfile-only execution (PLAN §§3.2, 17); capability records and typed error classification (PLAN §§6, 9); and the stdio-control/event-subscriber boundary (PLAN §1, item 4, and §5). Minimal process ownership, RSS supervision, finite breaker behavior, and orphan cleanup also address the locked supervision scope, once the safety defects above are corrected (PLAN §§1, 14).

Rev 1 should be defended or restored in these places:

- Preserve explicit human approval and a separate read-only Verifier. D7 weakens both Rev 1 §§1, 7, and 8, not merely ceremony.
- Preserve checkpoint-successor as the portable correctness mechanism and native resume/switch only as confirmed optimizations. Rev 1 §11 makes identity and completed-turn boundaries explicit; Rev 2 §13 currently crosses those boundaries during a limit.
- Preserve the Rev 1 §13 verbatim checkpoint core and deterministic selector as the MVP memory system. Context budgets are a useful Rev 2 addition, but bi-temporal mutation and LLM compaction should not become pause-path dependencies.
- Preserve exact-commit verification from Rev 1 §§8.3 and 14. Shared exploration may reduce navigation work, but it cannot replace independent inspection or count as verification evidence.
- Preserve Rev 1's explicit numeric transport limits, cleanup outcomes, complete test list, and finite state rules (Rev 1 §§6.2, 10, 17). Rev 2 should amend them in place rather than hide them behind “retained.”
- Preserve the non-ACP fallback seam from Rev 1 §§3.1, 4.2, and 5. Rev 2's broader headless research improves that seam, but Intent's single implementation is not enough evidence to remove the escape hatch.

## Scope and implementation order

In my judgment, the MVP is too fat as written even after honoring the locked requirement that “memory optimisation” include both supervision and context economics (PLAN §1, item 2). P1 is correctly first, but it cannot exit until the expanded transition table exists. P2 should implement safe process ownership, bounded queues, cancellation, verified reaping, and a simple finite breaker; the full RAM-tier/LRU policy should not precede the useful slice. P3 remains the right first product proof. P4 currently combines an uncollected classifier corpus, speculative forecast, pause/resume, two failover kinds, model switching, checkpoint-successors, memory selection, shared exploration, budgets, and restart recovery (PLAN §20; notes §3, items 1 and 5); that is more than one phase and its recorded-transcript exit gate depends on evidence the notes say is missing.

Split P4 into: (1) honest detection plus durable pause/manual resume, with exact `Retry-After` when available and `unknown` otherwise; (2) checkpoint-successor failover and confirmed model switching; (3) deterministic context selection/budgets and restart recovery. Keep the minimum locked supervision scope: safe child identity, soft/hard RSS handling, finite restarts, and no-orphan cleanup. Keep the minimum locked context-economics scope: provenance, deterministic selection, explicit budgets, and verbatim checkpoints.

If forced to cut, cut in this order: `harness serve`; D7; MCP session injection; learned ETA forecasting; bi-temporal/global memory and the LLM compactor; then LRU eviction and copied RAM tiers. Pause/resume still works with an honest unknown ETA, bounded manual/scheduled retry, and checkpoint-successor failover. The one under-invested area is failure-atomic state/operation design: exactly what is durable, what can be interrupted, what resumes, and what may be killed. That is more important to the flagship claim than a forecasted countdown.

## Final decision

**No-go for implementation from Rev 2 as written.** This is a conditional no-go, not a rejection of ACP or the vertical slice. Proceed only after all of these conditions are incorporated into the normative plan:

1. Replace §6.1 with an exhaustive phase/suspension/operation model and transition table covering limit, permission, approval, checkpoint, switch confirmation, breaker reset, user pause, cancellation, and interrupted recovery.
2. Define safe process identity and reaping, soft/hard watchdog behavior, worktree-taint validation, periodic safe checkpoints, non-disableable window and lifetime restart bounds, and storage/queue quotas.
3. Replace “checkpoint covers all work” with an honest synchronous mechanical checkpoint contract; make summaries optional and asynchronous; make mid-turn limit failover a successor operation.
4. Add a classifier corpus gate, cold-start `unknown` ETA, bounded probe policy, and tests that separate deterministic control invariants from real-provider forecast accuracy.
5. Add native resume semantics to the SPI and run the early ACP compatibility gate for both adapters before committing the rest of P2.
6. Reject the current D7, defer MCP injection and `serve`, and reduce memory to Rev 1's deterministic provenance model plus explicit context budgets.
7. Make Rev 2 self-contained and resolve the cost-accounting claim, SQLite driver gate, auth-status wording, and codex-acp binary provenance uncertainty called out in PLAN §§12, 17 and notes §3.

After those conditions, the appropriate decision is go for P1 through the offline vertical slice, with P4 split behind evidence gates.
