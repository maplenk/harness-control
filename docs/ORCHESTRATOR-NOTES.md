## 2. Decision reasoning + alternatives rejected

### D-transport (PLAN §3.1/§3.2, debate a+b)
Chose: ACP-uniform MVP (both official adapters), SPI transport-agnostic, Claude-SDK adapter fast-follow.
Reasoning: one conformance suite, one failure model, one permission-mediation path for MVP; Intent precedent de-risks the bet; Codex side has no better option (native SDK objectively weaker — spawn-per-turn, no permission callback); Claude native SDK IS objectively stronger, but adding a second transport in MVP doubles the P2 test matrix for a capability (token-granularity streaming, in-process canUseTool) the MVP flow doesn't strictly need.
Rejected alternatives: (i) best-surface-per-harness now (Claude SDK + Codex ACP) — better ceilings, more MVP surface area; (ii) headless-JSON everywhere (claude -p --input-format stream-json is genuinely capable and bidirectional) — no permission RPC on Codex side, hand-rolled session semantics; (iii) PTY — strictly dominated, all 8 harnesses have structured headless.
Weak point to attack: if #886-class adapter flakiness is systemic rather than transient, ACP-uniform could make the flagship switch flow unreliable at MVP; the fallback is checkpoint-successor which always works but loses native continuity.

### D-flagship detection (PLAN §13)
Chose: per-adapter classifier + 3-tier confidence + forecast engine.
Reasoning: ACP genuinely has nothing (closed StopReason enum verified); Claude adapter convention (errorKind) exists since Apr 2026; Codex structured snapshot never crosses (#227). The 3-tier vocabulary conveniently matches the user's design language (honored/forecast_fallback/forecast_only) — but note direction of inference: protocol reality independently produced the same tiers the user's mock assumed; I did NOT design from the mock.
Weak points: (1) live error-string characterization is an open research gap (harness-scout timed out before the addendum) — classifier fixtures start from recorded transcripts we don't yet have; (2) forecast engine is the most speculative component in the plan — per-provider window models fitted from observed resets could be wrong by hours; mitigation is honesty (source label + confidence) not accuracy; (3) probe-at-ETA burns a turn — on API-key billing that's cents, on limited plans it may re-trip the limit; jitter/backoff parameters are guesses.
Judgment call to review: I imported limit-pause MECHANICS (checkpoint-first, no-respawn, resume paths) from the user's design package despite "visuals only" — justified by the user separately confirming the feature in MVP. If reviewers think any imported mechanic is UI-fantasy rather than sound engineering, say so.

### D-supervision (PLAN §14)
Chose: pgid-based registry, RSS tree sampling, 75/100% thresholds, bounded restarts→breaker, RAM-scaled caps (Augment's exact tiers), LRU idle eviction.
Reasoning: Augment's numbers are production-tested defaults from a shipped product; copying beats inventing. Checkpoint-then-terminate at 100% (vs kill -9) preserves work; restarts counting toward breaker unifies OOM-kill and crash handling in one loop.
Weak points: (1) checkpoint-at-100%-RSS may be impossible if the child is thrashing — may need a hard ceiling above which we kill first and reconstruct from last periodic checkpoint (periodic checkpoint cadence is NOT yet specified in the plan — real gap); (2) watchdog termination during a child's git write can corrupt the worktree — worktree mutex covers add/remove, not arbitrary writes; termination should prefer SIGTERM+grace before SIGKILL and the verifier re-validates worktree cleanliness (partially specified, could be tighter); (3) LRU eviction of idle ACP processes assumes cheap resume — true only where session/load-or-resume is solid (Claude adapter yes; Codex resume = new process re-read, cost unknown).

### D-memory (PLAN §15)
Chose: ADD-only entries + bi-temporal invalidation + scope tiers + shared exploration artifact + per-role budgets + summarizing compactor (background job).
Reasoning: ADD-only (mem0) eliminates concurrent-writer conflicts (multiple agents write memory simultaneously); bi-temporal (Zep) fits spec supersession (old constraints stay queryable); summarizing compactor is the direct differentiator vs Intent's truncation — their weakness observed in code, not marketing.
Weak points: (1) risk of overbuilding — MVP has ONE implementor; concurrent-writer machinery is future-proofing that could be YAGNI (my defense: schema-level choices are cheap now, migrations later are not); (2) summarization-in-checkpoints introduces an LLM call into the pause path — pause must not BLOCK on it (write verbatim core synchronously, summarize async — this ordering is implied but not explicit in the plan; tighten if reviewers agree); (3) per-role budgets need numbers — I have none evidence-based yet.

### D-states (PLAN §6.1)
paused_limit as sibling-of-active (re-entrant from implementing/verifying/specifying) vs a substate: chose sibling for event-log clarity and UI mapping; cost is transition-matrix growth (limit during awaiting_approval? during model-switch confirm? — matrix not exhaustively enumerated in Rev 2, known gap, reviewers please enumerate).
breaker_open only from implementing/verifying — is that right? A coordinator (read-only) crash-looping should probably also breaker. Not settled.

### D-WS (PLAN §1.4/§18)
Position logged pre-research and survived it: stdio for control (process lifecycle = connection), WS as event-bus subscriber replaying from the SQLite sequence. AG-UI evaluated: right layer, but single-run abstraction lacks multi-agent hierarchy — custom event schema now, AG-UI mapping possible later. serve-in-MVP left to user (D4) because it's pure scope, not architecture.

### D-scope/ceremony (D7)
The usefulness risk is real: full flow = spec → human approval → implement → verify → merge-readiness = heavy for small tasks. --quick lowers to auto-approved micro-spec + combined implement/verify. Invariant question for reviewers: does auto-approval below a threshold break the "human owns the spec" principle, or is threshold-gated auto-approval (size/risk heuristic + always-overridable) an acceptable relaxation? My lean: acceptable and necessary; a tool nobody uses for small tasks loses the daily-driver position.
